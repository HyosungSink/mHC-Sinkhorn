# AscendC 算子性能优化方法：算子耗时超出基线解决方案

- source: https://www.hiascend.com/developer/blog/details/02195222162733793367
- section: Ascend C
- createTime: 20260815075214

AscendC 是昇腾 NPU 自定义算子开发语言，算子实测耗时超过设计基线是开发高频问题，常见根因：IO 访存带宽瓶颈、Tile 切分不合理、双 Buffer 流水线未启用、Vector 核利用率低、Global‑Local 数据搬运冗余、循环调度开销大。本文结合代码案例，从定位手段、典型问题修复、调优实践给出完整解决方案，面向 ATB/AI Core 算子开发。 1. 性能问题定位手段 优先使用工具确认瓶颈，再修改代码： 1.npusamplingprofiler：采集算子 trace，区分 AI Core 计算耗时、DDR‑L0/L1 搬运耗时； 2.AscendC‑prof：统计 Vector 利用率、Pipeline stall、指令周期； 3.关键指标：Vector 利用率 < 70% 一般为计算侧瓶颈；CopyGlobalToLocal占总耗时 60% 以上为访存带宽瓶颈。 基线：参考同类内置算子的 profiling 指标，自定义算子耗时超出基线 30% 以上，必须做调优。 2. 高频问题 1：Tile 切分不合理，单块 Tile 过小 / 过大 Tile 是 AscendC 核心，Tile 尺寸不匹配 L1 缓冲区大小，会造成频繁搬存或者片上缓存溢出。 错误示例：Tile 设置过小，循环次数过多，调度开销大。// bad: tile尺寸太小，循环次数爆炸 constexpr int TILE_LEN = 64; for(int64_t i = 0; i < total_len; i += TILE_LEN){     CopyGlobalToLocal(buf_gm, buf_l1, TILE_LEN); } 优化方案：Tile 大小对齐BURST(32B)，尽量占满 L1，减少循环轮次。// good tile策略，L1大小根据硬件规格，如910B L1约256KB constexpr int L1_SIZE = 256 * 1024; constexpr int DATA_SIZE = sizeof(float); constexpr int TILE_LEN = L1_SIZE / DATA_SIZE; //尽可能大tile，对齐burst  __global__ __aicore__ void MyCustomOp(GM_ADDR gm_in, GM_ADDR gm_out){     Pipe pipe;     LocalTensor l1_buf = pipe.AllocTensor(L1_SIZE);     int64_t total = GetGlobalTensorSize(gm_in);     for(int64_t offset = 0; offset < total; offset += TILE_LEN){         int64_t cur_tile_len = Min(TILE_LEN, total - offset);         CopyGlobalToLocal(gm_in[offset], l1_buf, cur_tile_len);         // vector计算逻辑         CopyLocalToGlobal(gm_out[offset], l1_buf, cur_tile_len);     } } 关键点：Tile 长度必须是 Burst（32 字节）整数倍，非对齐会触发多次小拷贝，带宽暴跌。 3. 高频问题 2：未使用双 Buffer 流水线，访存与计算串行 未开启双 Buffer 时，搬运数据完成之后才执行 Vector 计算，IO 与计算串行，AI Core 利用率低。 错误写法（串行执行）：// bad：串行，拷贝完再计算，流水线无法重叠 CopyGlobalToLocal(gm_in, buf0, tile_len); Compute(buf0, tile_len); CopyLocalToGlobal(gm_out, buf0, tile_len); 双 Buffer 优化代码，使用Pipe::Produce/ProduceEnd、Consume/ConsumeEnd实现访存‑计算并行：__global__ __aicore__ void DoubleBufferOp(GM_ADDR gm_in, GM_ADDR gm_out){     Pipe pipe;     constexpr int TILE_NUM = 2;     constexpr int TILE_LEN = 1024;     constexpr int TILE_BYTE = TILE_LEN * sizeof(float);      LocalTensor buf[TILE_NUM];     for(int i = 0; i < TILE_NUM; i++){         buf[i] = pipe.AllocTensor(TILE_BYTE);     }      int64_t total_elem = GetGlobalTensorSize(gm_in);     int64_t loop_cnt = (total_elem + TILE_LEN - 1) / TILE_LEN;      for(int64_t i = 0; i < loop_cnt; i++){         int buf_idx = i % TILE_NUM;         int64_t offset = i * TILE_LEN;         int64_t real_len = Min(TILE_LEN, total_elem - offset);          // 流水线Produce：异步搬运GM→L1         pipe.Produce(buf[buf_idx]);         CopyGlobalToLocal(gm_in[offset], buf[buf_idx], real_len);         pipe.ProduceEnd(buf[buf_idx]);          // Consume：上一块buffer做Vector计算，与当前块拷贝并行         int consume_idx = (i - 1 + TILE_NUM) % TILE_NUM;         if(i > 0){             pipe.Consume(buf[consume_idx]);             VectorCompute(buf[consume_idx], real_len);             CopyLocalToGlobal(gm_out[(i-1)*TILE_LEN], buf[consume_idx], real_len);             pipe.ConsumeEnd(buf[consume_idx]);         }     }     //处理最后一块tile     int last_idx = (loop_cnt -1) % TILE_NUM;     pipe.Consume(buf[last_idx]);     VectorCompute(buf[last_idx], Min(TILE_LEN, total_elem - (loop_cnt-1)*TILE_LEN));     CopyLocalToGlobal(gm_out[(loop_cnt-1)*TILE_LEN], buf[last_idx], Min(TILE_LEN, total_elem - (loop_cnt-1)*TILE_LEN));     pipe.ConsumeEnd(buf[last_idx]); } 双 Buffer 核心：当前 Tile 拷贝，同时上一个 Tile 执行计算，掩盖 DDR 访存延迟，大幅降低算子耗时。 4. 高频问题 3：Vector 核利用率低，循环内大量标量运算 Vector 单元是昇腾算力核心，尽量使用VectorXXX系列 API，避免循环内部大量 if‑else、标量计算。 错误写法：循环内部标量判断，Vector 流水线频繁 stall。// bad：循环内部标量if分支破坏向量化 for(int i=0; i 0) l1_buf[i] += 1.0f; } 优化：使用VectorCompare、VectorSelect向量化条件运算，消除分支：// good AscendC向量化条件计算 void VectorCompute(LocalTensor& in, int len){     LocalTensor tmp = in;     Vector vec_in = tmp;     Vector vec_one = 1.0f;     VectorMask mask = VectorCompareGT(vec_in, 0.0f);     Vector vec_res = VectorSelect(mask, vec_in + vec_one, vec_in);     vec_res.SaveToTensor(tmp, 0, len); } profiler 观察 Vector 利用率，如果低于 70%，重点排查是否存在大量标量逻辑。 5. 高频问题 4：冗余 Global‑Local 拷贝，重复搬运 GM 数据 同一个 Global 内存，多次执行 CopyGlobalToLocal，造成重复 DDR 访问，带宽被浪费。 优化原则：一次搬入 L1，多次复用，计算完成再写回 GM。 6. 主机侧调用与 tiling 优化（Tiling 函数） 算子性能差很多时候是 Host 侧 Tiling 切分不合理，切分过多 AI Core 任务，产生任务调度开销。Tiling 示例：extern "C" __attribute__((visibility("default"))) status_t MyOpTiling(     TilingContext* context){     auto in_shape = context->GetInputShape(0);     int64_t total_elem = in_shape->GetElementNum();     // 设置每个AI Core处理元素，不要过小     const int64_t PER_CORE_ELEM = 8*1024;     int64_t core_num = DivCeil(total_elem, PER_CORE_ELEM);     core_num = Min(core_num, 32); //910B最大可用AI Core数     context->SetBlockDim(core_num);     return 0; } BlockDim 不要设置过大，每个 AI Core 处理数据量不能太小，否则任务调度开销占比变高，整体耗时超过基线。 7. 通用调优排查清单（算子耗时超基线） 1.Profiler 看拷贝时间占比，如果 CopyGlobalToLocal 占比高：优化 Tile、开启双 Buffer，检查是否 Burst 对齐； 2.Vector 利用率低：消除循环内部 if‑else 标量分支，全部替换 Vector 接口； 3.Tiling：每个 AI Core 处理数据量不能过小，BlockDim 不要盲目设置最大； 4.禁止重复 CopyGlobalToLocal，L1 数据尽量复用； 5.内存地址对齐，GM 输入输出地址按 32B 对齐； 6.避免 LocalTensor 频繁 Alloc/Free，尽量在 Pipe 上一次性分配。 8. 总结 AscendC 算子实测耗时超出基线，优先通过 profiler 定位是访存瓶颈还是计算瓶颈。访存侧优先做 Burst 对齐、合理 Tile 切分、双 Buffer 流水线实现访存计算重叠，掩盖 DDR 延迟；计算侧消除循环标量分支，使用 Vector 系列接口提升 Vector 核利用率；Host 侧 Tiling 控制每个 AI Core 负载，避免任务调度开销。双 Buffer 流水线、Tile 尺寸、Vector 向量化、Tiling 分块是性能调优四大抓手。开发完成后对比基线，若仍然超出基线，再进一步看 PMU 硬件事件，分析 stall 周期，持续迭代优化。

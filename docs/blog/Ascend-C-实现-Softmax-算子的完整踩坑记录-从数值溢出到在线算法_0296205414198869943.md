六月份优化推荐模型的时候，profiling 发现 Softmax 层耗时占了整体推理的 12%，成了新的性能瓶颈。模型里有大量的 attention 机制，每个 attention head 都要算 Softmax，输入维度是 [batch, num_heads, seq_len, seq_len] = [16, 12, 512, 512]。PyTorch 的 Softmax 在昇腾上性能一般，而且后面通常接 CrossEntropyLoss，两个算子分开跑中间数据要反复搬运。决定用 Ascend C 写个高性能的 Softmax 算子，顺便把 Loss 计算融合进去。听起来 Softmax 公式就三步，实际写的时候才发现处处是坑，数值溢出、精度损失、在线算法、向量化每个环节都折腾了很久。从开始到优化完用了一个月出头，把 Softmax 的各种细节都摸透了。

需求这块先理清楚，Softmax 的公式是对输入 x 的最后一维做归一化。标准公式是 exp(x_i) / sum(exp(x_j))，看着简单但直接算会溢出。输入 x 如果有大的正数，exp(x) 会爆炸超过浮点数上限。标准做法是先减去最大值，变成 exp(x_i - max(x)) / sum(exp(x_j - max(x)))，这样指数部分都是非正数，不会溢出。但这需要两趟遍历，第一趟找最大值，第二趟算 exp 和 sum，第三趟做除法归一化。三趟遍历意味着数据要从 Global Memory 读三次，访存开销大。

开发环境用的 CANN 7.0.1，MindStudio 也更新到最新版了。Ascend C 的文档里有 Softmax 的简单示例，但只是个玩具代码，没考虑性能优化和数值稳定性。参考了些论文，发现有在线算法可以一趟遍历完成 Softmax，只需要读一次数据。在线 Softmax 的核心思想是动态维护最大值和累加和，每读一个元素就更新统计量。这个算法数值稳定而且省访存，但实现起来比三趟遍历复杂很多。

第一版实现还是按标准三趟遍历写，先把流程跑通再优化。第一趟用 ReduceMax 找最后一维的最大值，向量化处理一批元素，块内用 Max 指令取最大。多个块的结果再合并，最终得到全局最大值。这一趟写得还算顺利，向量化之后速度挺快。

第二趟算 exp 和 sum，每个元素减去 max 再做指数运算。Ascend C 有 Exp 向量指令，一次算一个向量的指数。但 Exp 指令精度有限，测试发现和标准库的 exp 函数有差异。输入在 -10 到 10 范围内误差还行，超出这个范围误差就大了。查了文档说 Exp 指令用的是查表加泰勒展开的方法，精度和性能的权衡。如果要高精度，要用标量的 exp 函数，但那样就没法向量化了。

权衡了下，决定用向量 Exp 指令，接受一定的精度损失。实际测试对模型精度的影响在 0.3% 以内，业务能接受。Exp 算完后要累加，ReduceSum 指令把一个向量的元素加起来。多个向量的和累加到一个标量，这个标量就是分母。

第三趟做归一化，每个元素除以 sum。除法比乘法慢，改成乘以 sum 的倒数。先算 1/sum，然后所有元素乘这个倒数。Reciprocal 指令算倒数，比除法快。但倒数的精度也有损失，sum 很小时倒数很大，放大了误差。加了个检查，sum 小于 1e-6 认为异常，直接输出全 0 或者均匀分布。

三趟遍历的版本跑起来，性能和 PyTorch 差不多，没啥优势。访存是瓶颈，三次读数据带宽占满了。Msprof 看到 NPU 利用率只有 40%，大部分时间在等数据。要优化只能减少访存，在线算法是唯一的路。

在线 Softmax 算法研究了好几天，看了论文《Online normalizer calculation for softmax》。算法的核心是维护三个变量：当前最大值 m，累加和 d，归一化因子。每读一个元素 x，先和 m 比较，如果 x > m 就更新 m，同时要修正 d。修正公式是 d = d * exp(m_old - m_new) + exp(x - m_new)。这个公式保证了 d 始终是基于当前 m 的累加和，数值稳定。

在线算法的实现很有挑战性，向量化特别难。每个元素处理时要更新全局的 m 和 d，向量内的元素不是独立的。研究了半天，发现可以分两步，先向量内并行找最大值和累加，然后再和全局的 m、d 合并。写了个向量版的合并函数，输入是向量的 max 和 sum，输出是更新后的全局 m 和 d。这个合并操作用了一些数学技巧，避免了逐元素的标量处理。

向量化的在线 Softmax 写了好几版才调通，边界条件特别多。向量内的元素要先做局部的 max 和 sum，然后和全局状态合并。合并时的 exp 计算要注意数值范围，m_old - m_new 可能很大，exp 会溢出。加了个判断，差值大于 20 就认为旧的累加和可以忽略，直接用新的。这个阈值是试出来的，exp(-20) 已经小到可以忽略了。

内存访问这次只需要一趟遍历，但要存储中间结果。算完 exp(x - m) 的值要保存下来，最后做归一化时要用。这些中间结果存在 L1 Buffer，如果 L1 放不下要写回 Global Memory。对于 seq_len = 512 的输入，一行 512 个 FP32 数，2KB，L1 能放几百行。Batch 大的时候要分批处理，一批算完再算下一批。

流水线优化加上了，计算和存储并行。当前行在计算时，上一行的结果写回 GM，下一行的数据预取到 L1。三个 Buffer 轮转，计算、写回、预取并行进行。Pipe 机制管理这三个阶段，Enque 和 Deque 控制节奏。流水线深度设成 3，平衡了内存占用和并行度。

数值精度又踩了个大坑，在线算法的累加和 d 会不断更新。每次更新都有舍入误差，累积起来误差挺大的。特别是 seq_len 很长的时候，更新几百次误差就不能忽略了。对比标准实现，误差能到 1e-3 的量级，超过了容忍度。研究了下发现是 FP16 精度不够，改成 FP32 计算后误差降到 1e-6。但 FP32 的计算慢，而且占内存。最后用了混合精度，输入输出是 FP16，内部计算用 FP32，兼顾了性能和精度。

向量长度的选择也试了几个，FP32 的向量长度是 64，FP16 是 128。用 FP16 向量处理输入，Cast 转成 FP32 做计算，结果再转回 FP16 输出。类型转换有开销，但比全程 FP32 快。测试了几组数据，混合精度比纯 FP32 快 30%，精度损失在可接受范围。

Softmax 的输出通常接 CrossEntropyLoss，融合这两个算子能省不少访存。CrossEntropyLoss 的公式是 -log(softmax(x)[target])，对于分类任务，target 是真实类别的索引。如果分开算，Softmax 输出写回 GM，Loss 再从 GM 读，一次往返。融合后 Softmax 的输出直接在 L0 Buffer 里取对应位置，算 log 和取负，不用经过 GM。

融合 Loss 的实现要处理索引，target 是个整数数组，指示每个样本的真实类别。根据 target 从 Softmax 的输出里取对应位置的值，这是个 Gather 操作。写了个向量化的 Gather，一次取多个样本的值。但 target 的索引是随机的，访问模式不连续，缓存命中率低。预取优化帮助不大，因为不知道下一次要取哪个位置。

Log 运算也有精度问题，Ascend C 的 Log 指令和 Exp 一样是近似计算。Softmax 输出的值在 0 到 1 之间，Log 的输入范围还好。但 Softmax 输出如果很小，接近 0，Log 会变成很大的负数，接近负无穷。这种情况要特殊处理，设个下限，小于 1e-7 的值当作 1e-7 处理。避免 Log 输出负无穷，导致 Loss 异常。

梯度计算也要写，CrossEntropyLoss 的反向传播。梯度公式是 softmax(x) - one_hot(target)，softmax 的输出减去 one_hot 编码的标签。这个梯度公式很简洁，实现起来也简单。但 one_hot 编码要生成，target 索引位置是 1，其他位置是 0。向量化生成 one_hot，用 Compare 指令判断当前位置是否是 target，生成 Mask，Mask 对应的位置是 1。

边界条件处理了一堆，输入的最后一维可能不是向量长度的整数倍。seq_len = 512 正好整除，但通用性要考虑任意长度。最后几个元素用 Mask 处理，只处理有效位。Mask 的生成要精确，边界元素不能漏掉也不能多处理。

性能测试终于看到明显提升，在线 Softmax 从三趟遍历的 8ms 降到 2.5ms，提升了 3 倍多。融合 Loss 后整个前向加反向从 15ms 降到 4ms，提升更大。整个模型的训练时间从 2.3s 降到 1.9s 每个 iteration，Softmax 不再是瓶颈。

不同输入规模测试了几组，seq_len 从 128 到 2048。seq_len 越长，在线算法的优势越明显，因为省的访存越多。seq_len = 2048 时提升能到 5 倍。batch size 的影响也测了，batch 大了并行度高，性能线性提升。

精度对齐验证了很久，在线算法和标准实现要完全一致。逐元素对比发现有些位置误差在 1e-6，主要是 FP16 和 FP32 混合精度导致的。纯 FP32 计算误差能到 1e-7，但性能慢 30%。业务评估了下，1e-6 的误差对模型收敛没影响，接受混合精度方案。

温度和功耗监控了下，Softmax 算子的 NPU 利用率提升到 70%，功耗从 8W 涨到 14W。总时间短了，能效比还是提升的。温度稳定在 65 度，散热没问题。

算子注册到 PyTorch 框架写了 ATen 扩展，torch.ops.load_library 加载 so 库。自定义 autograd.Function 包装前向和反向，梯度计算也用自定义算子。测试了梯度正确性，用 torch.autograd.gradcheck 验证，数值梯度和解析梯度一致。

单元测试写了几十个 case，各种输入形状、数值范围、边界情况都测到。对比 PyTorch 的 F.softmax 和 F.cross_entropy，前向和反向都要对齐。还测试了融合和非融合两个版本，验证融合算子的正确性。

实际训练跑了一周，模型收敛正常，精度没下降。Loss 曲线和用原生算子完全一致，证明自定义算子没有引入数值问题。训练速度提升了 15%，一个 epoch 从 2 小时降到 1.7 小时。

部署推理时也用上了，推理只需要前向，不需要反向和 Loss。单独导出 Softmax 算子，ONNX 格式。测试了推理性能，batch = 32 时单次 Softmax 1.8ms，吞吐量很高。

多线程并发测试了 8 个线程，每个线程独立的 Context。没有资源竞争，扩展性好。8 线程吞吐量是单线程的 7.5 倍，接近线性扩展。

错误处理加了输入检查，shape 不合法、数值异常都要报错。全 NaN 或者全 Inf 的输入直接拒绝，返回错误码。内存分配失败、指令超时也捕获异常，避免崩溃。

版本兼容性测试了 CANN 6.3 和 7.0，接口有些变化。用宏定义做适配，编译时根据版本选择代码路径。PyTorch 1.11、2.0、2.1 都测试了，接口兼容。

线上跑了两周，整理了上亿次 Softmax 计算，稳定性很好。没出现过崩溃或错误输出，监控数据正常。偶尔有几次性能抖动，看日志是系统调度问题，不是算子本身。

性能对比做了完整记录，PyTorch Softmax 8ms，自定义单算子 2.5ms，融合 Loss 算子 4ms（含前向反向）。端到端训练从 2.3s 降到 1.9s 每 iteration，吞吐量从 14 samples/s 提升到 17 samples/s。训练时间节省 17%，成本下降明显。

开发投入一个月，代码 3500 行，包括前向、反向、融合版本、测试。性能提升 3 倍，而且算子可以复用到其他模型，Transformer、BERT、GPT 都能用。团队对 Ascend C 的掌握度也提升了，后续开发效率更高。

后续优化还想试试 FlashAttention 的思路，把 Softmax 和 Attention 的矩阵乘法融合。整个 Attention 模块一个算子搞定，访存优化到极致。还想研究 RoPE 位置编码，和 Attention 融合也有空间。这些都列在计划里，有时间继续优化。

文档整理了完整的开发笔记，在线 Softmax 算法的推导、实现细节、优化技巧都记录了。数值稳定性的分析也写得很详细，给后续开发参考。代码注释加得很足，关键算法都解释了原理和数学依据。

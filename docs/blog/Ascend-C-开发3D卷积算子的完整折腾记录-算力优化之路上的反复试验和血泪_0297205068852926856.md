# Ascend C 开发3D卷积算子的完整折腾记录，算力优化之路上的反复试验和血泪经验；

年前接到任务，要在昇腾平台上实现一个高效的3D卷积算子，用于一个基于时间序列的视频分析项目。视频输入是 [8, 32, 112, 112, 3] 的形状，每次处理32帧视频的8个样本，模型复杂核心算子是3D卷积。PyTorch自带的3D卷积在昇腾上性能不理想，单次推理要1.8秒，达不到实时性能需求。研究后发现只能自己写Ascend C算子。听说过Ascend C可以贴近硬件直接操控，但之前一直没机会接触，这次算是从零开始硬啃，场面一度非常惨烈。

一开始还是想着用PyTorch的扩展功能，基于ATen自定义算子接口来封装分块和调度，但性能上基本没什么突破。搞明白流程后发现还是Ascend C能更低层次直接操作内存和数据流水线，能彻底避免框架调度中耗时低效的部分。于是咬咬牙决定用Ascend C原生语言开发一个自己的3D卷积算子。参考了手头的文档，Ascend C介于C语言和类似CUDA的开发模型之间，但坑和文档不对称的地方实在太多，完全是另一个世界的开发环境。

开发环境一开始就折腾了很久。先是装CANN套件，我装的是7.0版本，还得下载配套的编译器ccec配置环境变量。MindStudio虽然方便调试，但占用资源大，每次运行特别吃内存。用命令行直接跑也可以，但调试比IDE难多了。编写Ascend C算子需要明确数据流设计，Ascend的内存分层（Global Memory、L1、L0）决定了性能的天花板。内存拷贝要用DataCopy指令，显式从Global Memory搬数据到L1，再进入L0完成单指令向量化计算。没搞清楚内存分层之前，代码运行起来就是段错误，完全不知道问题在哪。

算子代码分成好几部分：输入和输出的形状推导，内存分配和数据的搬运，核函数的向量化实现，以及算子的注册调用。初版实现了一个简单的3×3×3卷积，数据分片和Tiling策略都很原始，基本上就是按照输入形状一层层遍历逐元素计算。跑了第一版代码之后，性能只能勉强和PyTorch的原生算子打平，甚至在更大输入上速度反而更慢。问题很明显：没有利用向量化能力，手写的寄存器复用太低，内存访问也存在很多不必要的搬运。

了解硬件机制花了不少时间，搞懂流水线和指令调度后，重新设计了数据访问模式。像视频这种5维数据，时间维是核心维度，输入张量在时间维上要分段加载到L1，所有块处理中尽量减少L1到Global Memory的回写。调整了块大小和时间段切片策略后，L1的使用效率提升了30%，访存瓶颈有了明显改善。随后接入流水线技术，把数据加载、计算和写入分成并行阶段，几个循环做了重叠，用Enqueue和Deque操作确保数据流畅。

向量化是又一个痛点，Ascend C的向量化和普通标量循环完全是两种思想。每个指令组操作一个数据向量，长度受硬件向量寄存器限制。单次能处理的最大向量是一批128个FP16数据，但边界条件的处理很麻烦，零填充和Mask指令要精确控制。第一次写的向量化代码根本跑不通，报了多个越界错误。Debug发现问题主要是边界块处理没考虑到向量宽，最后一个块总是超出内存边界。加了额外的条件分支后稳定性提升了，但向量化并行率下降。

稀疏优化也是需要重点解决的点，卷积过程中很多权值是零值，沿用常规方法无疑浪费了宝贵的计算资源。改用稀疏矩阵存储格式（Block CSR），非零元素直接参与运算。配合Mask操作，向量处理时可以跳过零权重元素，节约了大量计算开销。但稀疏矩阵需要特殊的加载顺序，重构了块索引规则才保证所有非零块正确参与运算。同时对于权重部分使用了存储压缩，权重块重复利用率更高了。

算子性能优化中最大的收获来自流水线优化，3D卷积的输入输出数据量巨大，优化指令和内存寻址的顺序起到了关键性作用。起初在Prof工具里看到访存耗时占了一半以上，后来通过调整不同计算阶段的数据交错，伪流水线效率推到极限时，计算占比终于超过70%。链条调度时加了双Buffer机制，计算和加载同时进行，吞吐率进一步提升。

最后测试时才算是比较有成就感，稠密卷积场景下比原生算子快了1.5倍，稀疏模式下的矩阵时间进一步缩减到PyTorch原生算子的四分之一。同时台积MC级功耗检测，长周期缓存率均优越近3xxx% !!

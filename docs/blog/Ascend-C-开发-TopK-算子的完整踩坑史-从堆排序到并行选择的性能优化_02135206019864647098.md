一月份做推荐系统部署，召回阶段要从几万个候选 item 里选出 top-100 个分数最高的，这个 TopK 操作在整个推理流程里耗时特别长。输入是 [batch, 50000] 的分数矩阵，要对每个 batch 找出最大的 100 个值和对应的索引。PyTorch 的 torch.topk 在昇腾上只有 CPU 实现，单次要 45ms，batch=32 时总共 1.4 秒，比模型推理还慢。数据在 NPU 和 CPU 之间反复搬运，白白浪费带宽。查了一圈发现昇腾平台没有高效的 TopK 算子，只有个基础实现性能很差。研究后决定用 Ascend C 自己写，把 TopK 搬到 NPU 上跑。听起来就是找最大的 K 个元素，实际开发时才发现排序算法选择、堆维护、并行策略、内存访问每个环节都是坑。从开始到优化完用了快两个月，把 TopK 的各种实现方法、优化技巧、边界情况全摸透了。

需求这块先说清楚，TopK 算子要从输入张量的某个维度找出最大或最小的 K 个元素。输入是任意形状的张量，指定维度 dim 和数量 K，largest 参数控制找最大还是最小。输出是两个张量：values 是排序后的 K 个值，indices 是对应的索引。比如输入 [32, 50000]，dim=1，K=100，largest=True，输出 values [32, 100] 和 indices [32, 100]，每行是该行最大的 100 个元素。关键难点有几个：第一是 K 很小但输入很大，全排序浪费，要用选择算法；第二是要返回索引，排序时要同时移动索引；第三是 largest 和 smallest 要分别处理；第四是 sorted 参数，控制输出是否排序，False 时只需要找到 K 个元素即可。

开发环境用的 CANN 7.0.1，MindStudio 也是最新版。Ascend C 的文档里没有 TopK 的参考实现，只能自己研究算法。参考了经典的 TopK 算法：全排序、部分排序、堆选择、快速选择。全排序最简单但最慢，O(N logN)。部分排序稍好，O(N logK)。堆选择维护大小为 K 的最小堆，O(N logK)。快速选择基于快排的 partition，平均 O(N) 但最坏 O(N^2)。

第一版实现用的最简单的方法，全排序然后取前 K 个。对每行 50000 个元素用快速排序，排序时同时移动索引。写了个 qsort_with_indices 函数，输入是 values 数组和 indices 数组，原地排序。快排的实现参考了标准库，递归分治，pivot 选中位数。但递归深度不好控制，栈空间有限。改成迭代版本，用栈模拟递归，自己管理栈空间。

第一版跑起来性能惨不忍睹，单次 TopK 要 120ms，比 CPU 还慢一倍多。全排序 50000 个元素太慢了，而且只需要前 100 个，后面 49900 个的排序完全浪费。向量化也没做，标量比较和交换，效率低下。

堆选择算法实现了第二版，维护大小为 K 的最小堆。遍历输入的每个元素，如果大于堆顶就替换堆顶并调整堆。最后堆里的 K 个元素就是最大的 K 个。写了个 min_heap 的数据结构，支持 insert、pop、heapify 操作。堆用数组表示，父节点 i 的子节点是 2i+1 和 2i+2。Heapify 向下调整，insert 向上调整。

堆选择的时间复杂度是 O(N logK)，比全排序好。测试了下性能提升到 60ms，快了一倍。但还是不够快，堆操作都是标量的，每次调整要比较和交换多次。而且堆的结构决定了很难向量化，父子节点的关系是动态的。

快速选择算法试了第三版，基于快排的 partition 思想。选一个 pivot，把数组分成大于和小于 pivot 的两部分。如果小于部分的数量等于 K，那就是答案。如果小于 K，递归到大于部分。如果大于 K，递归到小于部分。平均复杂度 O(N)，理论上最优。

快速选择写起来不难，但 pivot 的选择很关键。随机选 pivot 平均性能好，但最坏情况会退化到 O(N^2)。用三数取中法，选首、中、尾三个数的中位数作 pivot。测试了几种 pivot 策略，三数取中最稳定。

快速选择的性能测试了下，平均 40ms，比堆选择快 30%。但有些输入会退化，比如全是相同的值，partition 完全不平衡。加了随机化，打乱输入顺序，避免最坏情况。

但快速选择有个问题，找到的 K 个元素是无序的。如果 sorted=True，还要再排序一次。额外排序 K 个元素，O(K logK)，K=100 时还能接受。用快排对找到的 K 个元素排序，整体复杂度 O(N + K logK)。

向量化优化试了很多方法，排序和选择都不是规整的操作，很难向量化。试了 Bitonic Sort 双调排序，这个算法是比较交换网络，可以向量化。但 Bitonic Sort 要求长度是 2 的幂次，50000 不是，要填充。填充到 65536，浪费内存和计算。测试了下性能，向量化的 Bitonic Sort 比标量快排还慢，因为比较次数太多。

并行策略调整了，按 batch 并行。每个 batch 的 TopK 独立，分配不同的 Block。Batch=32，每个 Block 处理一行 50000 个元素。多个 Block 并行，充分利用多核。测试了下性能提升到 25ms，快了很多。

分块选择优化了并行度，50000 个元素太多，一个 Block 处理不过来。把一行分成多个块，每个块 1000 个元素。每个块独立找 TopK，然后合并结果。比如 50 个块每个找 Top100，得到 5000 个候选，再从 5000 个里找最终的 Top100。这样每个块的计算量小，多个块并行，整体更快。

合并策略也有讲究，50 个 Top100 合并成最终 Top100。简单方法是把 5000 个元素再做一次 TopK，但还是慢。优化方法是多路归并，每个块的 Top100 已经排序，用归并排序的思想合并。维护一个大小为 50 的堆，每个块的当前最大元素入堆。每次取堆顶，对应块的下一个元素入堆。取 100 次得到最终结果。

多路归并的实现写了个 multiway_merge 函数，输入是 N 个排序数组，输出是合并后的 TopK。堆的大小是 N，每个元素包含值、来源块索引、块内索引。Heapify 和 pop 操作维护堆的性质。测试了下合并的时间，50 个数组合并 Top100 只要 0.5ms，很快。

内存访问优化也做了，分块时每个块的数据预加载到 L1 Buffer。1000 个 FP32 元素 4KB，L1 能放下很多块。预加载后减少 GM 访问，提升访存效率。但不同块的访问是顺序的，Cache 命中率还行。

索引的维护比较麻烦，排序和选择过程中要同时移动索引。初始化时索引是 0, 1, 2, ..., N-1。每次交换元素时，索引也要交换。写了个 swap 函数，同时交换 value 和 index。测试的时候发现索引经常对不上，调了很久才发现是某些分支忘了更新索引。

Largest 和 smallest 参数的处理用了比较函数。Largest=True 时，比较函数是 a > b。Smallest=True 时，比较函数是 a < b。写了个 comparator，根据 largest 参数返回不同的比较函数。所有排序和选择都用这个 comparator，逻辑统一。

Sorted 参数的处理也优化了，sorted=False 时不需要最后的排序。快速选择找到 K 个元素直接返回，省掉 O(K logK) 的排序时间。测试了下 sorted=False 比 sorted=True 快 15%。

边界情况处理了一堆，K=0 直接返回空，K >= N 返回全部元素排序。K=1 的情况优化了，只需要找最大值，一趟遍历 O(N)。N 很小的情况也优化了，N < 1000 时直接用插入排序，简单高效。

数值精度这次倒是没啥问题，TopK 只是比较和选择，不涉及浮点运算。但要注意 NaN 的处理，NaN 和任何数比较都是 False。遇到 NaN 怎么办？PyTorch 的策略是 NaN 排在最后，实现时特殊处理。比较时先判断是否 NaN，NaN 永远当作最小（或最大）。

Inf 的处理也要注意，正无穷大于所有数，负无穷小于所有数。测试了输入全是 Inf 或者混有 NaN 的情况，都要能正确输出。

性能测试终于看到明显提升，优化后的 TopK 从 120ms 降到 12ms，提升了 10 倍。对比 CPU 的 45ms，快了近 4 倍。不同 K 值测试了，K=10 是 8ms，K=100 是 12ms，K=1000 是 25ms，K 越大越慢。

不同输入大小测试了，N=10000 是 5ms，N=50000 是 12ms，N=100000 是 28ms，基本线性增长。

不同 batch 测试了，batch=1 是 0.5ms，batch=32 是 12ms，batch=64 是 22ms，也是线性。

功耗和温度监控了下，TopK 算子的 NPU 利用率 50%，主要是分支和比较操作。功耗 11W，温度 59 度，散热没问题。

算子注册到 PyTorch 框架写了扩展，接口和 torch.topk 一致。输入是 input, k, dim, largest, sorted。dim 参数支持任意维度，不只是最后一维。多维的处理是把其他维度展平，对指定维度做 TopK。

单元测试写了几十个 case，各种 K 值、各种输入大小都测到。对比 PyTorch 的实现，values 和 indices 完全一致。还测试了边界情况，K=0、K=N、输入有 NaN、输入有 Inf，各种组合。

实际部署在推荐召回系统上，整个召回流程测试了端到端性能。召回时间从 1.5s 降到 0.8s，TopK 不再是瓶颈。召回准确率没有变化，和 CPU 版本完全一致。

广告排序、搜索排序这些场景也测试了，都用到 TopK。性能都有 3-4 倍的提升，效果很明显。

多线程并发测试了 4 个线程，每个线程处理一个请求。TopK 算子内部无状态，线程安全。4 线程吞吐量是单线程的 3.8 倍，扩展性不错。

错误处理加了输入检查，K 要在 [0, dim_size] 范围。dim 要在 [-ndim, ndim) 范围。输入不能是空 Tensor。内存分配失败要捕获，返回错误码。

版本兼容性测试了 CANN 不同版本，7.0 和 6.3 接口一致。PyTorch 1.11、2.0 都能用。ONNX 导出支持，TopK 是标准算子。

线上运行了三周，处理了数千万次 TopK 操作，稳定性很好。没出现过错误输出，性能监控正常。偶尔有几次超时，都是 K 值异常大导致的，K 接近 N 时退化成全排序。加了 K 值的限制，K 超过 N/2 时报警。

性能对比记录了数据，CPU TopK 45ms，自定义 NPU 12ms，提升 3.8 倍。端到端召回从 1.5s 降到 0.8s，QPS 从 0.67 提升到 1.25。吞吐量接近翻倍，效果很好。

成本收益算了下，开发两个月，代码 3600 行。性能提升 4 倍，推荐服务吞吐量提升 85%。服务器数量能减少 45%，成本节省明显。TopK 是基础算子，推荐、搜索、排序都能用，复用价值高。

后续优化还想试试，基数选择算法，利用数值分布做桶排序。GPU 上有 radix select 的实现，效果不错。还想研究 approximate TopK，允许误差换取速度，推荐场景能接受。这些列在计划里，有时间继续优化。

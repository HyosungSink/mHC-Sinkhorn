# 大模型融合算子开发实战：Cube 与 Vector 协同，手写一个 Attention 前处理融合算子

引言：为什么融合是大模型推理的必答题 大模型推理的性能瓶颈，很多时候不在算力，在"零碎"。 一个 Attention 前处理，可能要串一串小算子：RmsNorm 归一化 → RoPE 旋转位置编码 → 量化。每个算子单独看都不复杂，但它们串起来的代价很可观： ●kernel 下发开销：每个算子都是一次独立的 kernel launch，几十个小算子就是几十次下发，下发本身有固定开销； ●GM 往返搬运浪费：前一个算子把中间结果写回 GM（全局内存），后一个再从 GM 读回来。中间结果本来可以完全待在片上（UB），却被迫"出片又进片"，白白浪费带宽。 融合的解法一句话就能说清：把这一串小算子合成一个 kernel，中间结果驻留片上不回 GM，一次下发完成全部计算。融合前：  RmsNorm ──GM──> RoPE ──GM──> Quant     （3 次下发 + 2 次 GM 往返） 融合后：  [ RmsNorm → RoPE → Quant ]             （1 次下发，中间结果全在 UB） 官方在这方面已经做出了标杆——针对 DeepSeek 的 MLA 前处理，昇腾 CANN 做了两级融合： ●VV 融合（多个 Vector 算子融合）：把 MLA 预处理的两条计算流分别融成 2 个融合算子，单算子性能直接翻倍，在 DeepSeekV3 整网中取得 5%+ 的计算性能提升； ●超级大算子 MLAPO（MlaPreprocessOperation）：进一步把前处理的 13 个小算子融成一个，通过 Vector 与 Cube 的并行流水把较短的 Vector 耗时基本掩盖，单算子耗时从 109μs 降到 45μs，在 VV 融合基础上性能再次翻倍，整网提升 20%+。 但官方文章讲的是"成果"，这篇文章我想带你走一遍"过程"：作为一个普通开发者，如何从 0 到 1 手写一个小规模融合算子，理解 MLAPO 背后的设计方法论。 一、融合的层次：先想清楚你要做到哪一步 融合不是一上来就追求"13 合 1"。按难度和收益，我把它分成三层，按需选型很重要： 层次 组合 难度 收益 适合谁 VV 融合 Vector + Vector ★ 低 省 GM 往返 入门首选，性价比最高 CV 融合 Cube + Vector 协同 ★★ 中 还能做流水掩盖 有一定经验的开发者 超级大算子 MLAPO 式多模块融合 ★★★ 高 整网级提升 官方/资深团队 几个选型心得： ●先从 VV 融合练手。RmsNorm、RoPE、激活、量化这些大多是 Vector 计算，把它们融在一起，不涉及 Cube/Vector 的复杂协同，却能把"中间结果驻留 UB"这个核心思想吃透。 ●CV 融合的真正价值不只是省搬运，而是流水掩盖——让 Vector 的耗时藏在 Cube 计算的阴影里。这是 MLAPO 的核心思想，也是本文的重点。 ●超级大算子慎碰，它对框架、调度、显存管理的要求是另一个量级，先把前两层玩熟。 本文的实战对象，我选了一个规模适中、又能完整展示 CV 协同思想的目标：RmsNorm + RoPE + 量化 的三合一融合。这正是 MLA 前处理的真实子结构——以 DeepSeekV3 为例，Q 和 KV 降维后都要过 RmsNorm，每个 Head 切分出的一部分（RoPE 维度）要做 RoPE，最终还要量化——所以"归一化→旋转→量化"这一串，天然就是个可融合的小算子链。 二、实战：RmsNorm + RoPE + 量化 三合一 2.1 先立基线：融合前的 profiling 动手前必须先量化现状，否则融合有没有收益都不知道。先把三个独立算子用 msProf 各跑一遍，记录它们各自的耗时：RmsNorm   —— 读 x → 算均方根 → 归一化 → 写回 GM RoPE      —— 读回 → 旋转 → 写回 GM Quant     —— 读回 → 量化 → 写回 GM ------------------------------------------------- 合计 = 三者耗时之和 + 2 次中间结果 GM 往返 这里要记下两件事：三个算子的总耗时，以及中间结果在 GM 上进出的数据量。后者就是融合要干掉的目标——把你测出的真实数字填进去，就是这篇文章的基线。 2.2 数据流设计：中间结果驻留 UB 融合的核心设计就一句话：x 从 GM 读进来一次，RmsNorm 的结果留在 UB，直接喂给 RoPE，RoPE 的结果再留在 UB 喂给量化，最后只把量化结果写回 GM 一次。// 伪代码示意 CopyIn(x);                    // GM → UB（仅 1 次） rmsnorm_out = RmsNorm(x);     // 结果驻留 UB，不写回 rope_out    = RoPE(rmsnorm_out);  // 还在 UB quant_out   = Quant(rope_out);    // 还在 UB CopyOut(quant_out);           // UB → GM（仅 1 次） 对比一下：融合前中间结果要 GM 往返 2 次，融合后 GM 只进出各 1 次。访存密集的小算子串，省下的带宽往往比省下的计算更值钱。 2.3 Tiling 统一设计：三段共享一套切分 这是融合算子最容易踩坑的地方。三个算子原来各有各的 Tiling，融合后必须共用一套切分，否则中间结果在 UB 里的布局对不上。 设计原则： ●选一个对三者都兼容的基础 tile 形状（通常按最小公约束取，比如都按 head_dim 或某个对齐单位切）； ●三段计算用同一份 Tiling 参数驱动，保证第 i 个 tile 在三个阶段指的是同一段数据； ●UB 空间要按"三段里峰值占用"来分配，注意 double buffer 会翻倍。// 一份 Tiling，三段共用 struct FuseTiling {     uint32_t tileLen;      // 每个 tile 的长度（三段通用）     uint32_t tileNum;     uint32_t headDim;     // ... }; 经验：如果某一段的访存模式和另外两段差异太大（比如 RoPE 需要按 (cos, sin) 交错访问），不要硬融——可以在 RoPE 内部做一次 UB 内的局部重排，仍保持对外是同一份 Tiling。 2.4 MIX 模式下的 AIC/AIV 协同：Set/WaitFlag 实战 到这里是本文的硬核部分。如果 Attention 前处理里还混着一段 Matmul（比如 QKV projection），那就需要 Cube（AIC）算 Matmul、Vector（AIV）算 Norm/RoPE，两者协同。 昇腾 MIX 模式下，AIC 和 AIV 是异步并行的，跨核的数据依赖必须用旗语同步，否则就是上一篇讲过的"数据踩踏"：// AIC 侧：Matmul 算完，置旗 if (ASCEND_IS_AIC) {     MatmulCompute();                       // Cube 计算     CrossCoreSetFlag<...>(FLAG_MM_DONE);   // 通知 AIV：Matmul 好了 }  // AIV 侧：等旗，再做 Vector 后处理 if (ASCEND_IS_AIV) {     CrossCoreWaitFlag<...>(FLAG_MM_DONE);  // 等 Matmul 完成     RmsNormRopeQuant();                    // Vector 后处理 } 关键纪律：每一对 CrossCoreSetFlag/WaitFlag 必须严格配对，旗语 ID 不能复用串扰。漏一个 Wait，就是偶发精度错误；多等一个不该等的旗，就是死锁。这类 bug 单核调不出来，务必在多核 MIX 模式下充分验证。 三、流水掩盖：让 Vector 藏进 Cube 的阴影里 这是融合算子性能的最高境界，也是 MLAPO 的核心思想。 观察一个事实：Cube（矩阵乘）和 Vector（归一化/激活/量化）用的是不同的硬件单元，理论上可以同时跑。如果能让它们流水线化——Cube 在算第 i 块的时候，Vector 在处理第 i-1 块的结果——那么 Vector 的耗时就被"掩盖"掉了，理想情况下总耗时趋近于只有 Cube 部分的时间。无掩盖（串行）： AIC:  [MM0][MM1][MM2] AIV:        [V0]  [V1]  [V2]        ← 等 Cube 全算完才开始 总时长 = MM全部 + V全部  流水掩盖（并行）： AIC:  [MM0][MM1][MM2] AIV:       [V0]  [V1]  [V2]         ← 边算边追，藏在 Cube 阴影里 总时长 ≈ MM全部 + 最后一段V （上图是原理示意：横轴是时间，每个方框代表一个数据块的计算。串行时 Vector 要等 Cube 全部算完才启动；并行流水时 Vector 跟随 Cube 逐块处理，总时长被压缩到接近只有 Cube 的时间。） 实现上靠的就是多级流水 + 双缓冲 + 旗语：AIC 每算完一块就 Set 一个旗，AIV 拿到旗就处理上一块，两者用不同的 UB buffer 错开。掩盖得充分时，Vector 部分对总时长的贡献就只剩收尾那一段。 这也是为什么我说 CV 融合的价值不只是省搬运——省搬运是线性的，流水掩盖是"结构性的提速"。 四、用 msProf 验证：看流水图说话 融合有没有真起作用、流水掩盖做没做到位，不能凭感觉，要看 msProf 的仿真流水图。 把融合前后的 simulator pipeline 图导出来对比，重点看三条流水的占比变化： 流水 融合前 融合后 说明 MTE2（搬运） 高，频繁 GM 往返 明显下降 中间结果不再回 GM Vector 各算子零散出现 连续且部分被 Cube 掩盖 流水化 Cube 单独一段 与 Vector 交叠 并行 如果融合后 MTE2 占比没有明显下降，说明中间结果还在偷偷回 GM（检查你的数据流设计）；如果 Vector 和 Cube 还是完全串行、没有交叠，说明流水掩盖没做成（检查旗语和双缓冲）。流水图是融合算子的"成绩单"，一定要会读。 五、收益怎么算 + 怎么在你自己的模型里找融合机会 收益从哪来：这个三合一融合的收益主要有两块——一是省掉了中间结果的 2 次 GM 往返（访存），二是 Vector 部分被 Cube 部分掩盖（流水）。具体到你的算子和 shape 能提升多少，必须用你在 2.1 节测的基线减去融合后的实测耗时来算，没有放之四海皆准的固定百分比。可参考的对标是官方 MLAPO：单算子从 109μs 降到 45μs（109/45≈2.4 倍）——但那是把 13 个算子融合、且做了充分流水掩盖的结果，你这个三合一的规模小得多，收益自然也更有限，别直接套用。 这里要特别提醒一个容易被误读的点：上面这些都是单算子级的提升。官方 MLAPO 那 20%+ 是整网性能提升——单算子性能翻倍（109→45μs）不等于整网翻倍，因为前处理只是整网推理的一部分，遵守阿姆达尔定律。两个口径别搞混：单算子的提升空间可以很大，落到整网会被其他未优化部分摊薄。你报收益时务必注明是单算子还是整网口径。 最后把方法泛化一下。怎么判断你的模型里哪里值得融合？ 我的经验是找满足这两个特征的算子串： 1.访存密集：单个算子计算量小、但读写量大（Norm、激活、量化、逐元素操作都是典型）； 2.相邻依赖：一个的输出紧接是下一个的输入，中间没有分支。 满足这两条，融合几乎稳赚——省搬运、省下发、还能进一步做流水掩盖。反之，计算本身就很重的大算子（大 Matmul），融合的收益边际递减，不必硬融。 结语 三篇走到这里，脉络其实是一条线：先把算子调对（精度排查），再学怎么快开发（CATLASS 模板库），最后攻克性能天花板（融合算子）。 融合算子是大模型推理里技术密度最高的活，但拆开看，它的方法论并不玄：数据流上让中间结果驻留片上，调度上让 Cube 和 Vector 流水掩盖，工程上用旗语把跨核同步管住。MLAPO 那样的大融合，无非是这三条原则在更大规模上的应用。 建议的进阶路径：先用 VV 融合把 RmsNorm+RoPE+Quant 这类小串跑通、跑出有数据支撑的收益，再尝试加入 Cube 做 CV 协同，最后再去看 MLAPO、FlashAttention 的源码——那时你会发现，那些曾经高深的东西，你已经能看懂了。 参考与学习资源 ●《CANN 创新 MLAPO 算子，DeepSeek 模型推理效率倍增》（昇腾社区官方技术文章） ●Ascend C 算子开发指南（MIX 模式 / 跨核同步章节） ●msProf 上板调优与 simulator 仿真调优文档

# Ascend C 自定义算子开发的血泪史，从入门到优化 MatMul 算子的完整踩坑记；

- section: Ascend C
- createTime: 20260128085759

一月份项目里有个矩阵乘法的特殊需求，PyTorch 自带的 matmul 在昇腾 NPU 上跑性能不够好，而且我们的矩阵有稀疏性可以优化。查了下要自己写算子，昇腾平台用 Ascend C 语言开发。看着文档一脸懵，这玩意儿类似 CUDA C 但又不完全一样。从零开始学到把自定义算子跑起来并且性能超过原生算子用了整整两个月，Ascend C 的坑真是一个接一个，把学习过程和踩过的坑记录下来。

背景需求这块先说下，做的是推荐系统的 Embedding 层计算，矩阵是 10000x512 乘以 512x256 的规模；特点是第一个矩阵很稀疏，90% 的元素是 0；PyTorch 的通用 matmul 不管稀疏性，所有元素都算一遍；理论上可以跳过零元素，只算非零部分，性能能提升好几倍；昇腾 910B 的 NPU 算力够强，就是缺个稀疏矩阵乘法的算子；

开发环境搭建第一关就卡住了，Ascend C 开发要装一堆工具链；CANN toolkit 是基础，装了 7.0 版本，安装包 3GB 多；Ascend C 编译器 ccec 包含在 CANN 里，但要单独配置环境变量；source 了 set_env.sh 脚本，加载了一堆路径；MindStudio 也装了，IDE 能调试算子，界面和 VSCode 类似；

第一个 HelloWorld 算子跟着官方教程写，简单的向量加法；代码结构分成几部分：核函数、算子信息库、算子实现；核函数是 global 修饰的，在 NPU 上执行；算子信息库定义输入输出类型、shape 推导；算子实现调用核函数，注册到框架；

编译就遇到问题了，ccec 的报错信息特别不友好；syntax error，也不说哪一行哪个字符；加 -v 参数看详细日志，一堆信息里找关键错误；原来是头文件路径没配对，#include "kernel_operator.h" 找不到；ASCEND_TENSOR_COMPILER_INCLUDE_PATH 环境变量要设对；

编译通过后生成 .o 文件和 .json 文件，打包成算子包；om_generator 工具把算子注册到系统；但运行时又报错，找不到算子实现；排查发现是算子名字不一致，核函数名、注册名、调用名要完全匹配；改了好几个地方才对上；

调试环境配置也费劲，Ascend C 不像 CUDA 有 cuda-gdb；MindStudio 的调试功能要配置，连接开发板通过 SSH；打断点、单步执行这些基本功能都有；但变量查看不太好用，复杂结构体显示不全；主要还是靠打印日志调试，printf 在核函数里能用；

内存管理是第一个大坑，Ascend C 的内存分几种，Global Memory、L1 Buffer、L0 Buffer；Global Memory 是 HBM 高带宽内存，容量大但慢；L1 Buffer 类似 L1 Cache，容量小但快；L0 Buffer 是向量计算单元的本地内存，最快；

数据搬运要显式写代码，DataCopy 接口从 GM 拷贝到 L1；CopyIn 和 CopyOut 在 L1 和 L0 之间搬运；每次拷贝的大小要对齐，32 字节对齐或者 Block 对齐；一开始不理解对齐，随便写个大小，运行时段错误；查文档发现要用 GetBlockNum 计算 Block 数量；

Tiling 策略也要自己设计，大矩阵分成小块处理；每个 Block 处理一部分数据，多个 Block 并行；Tiling 的粒度影响性能，太大了 L1 放不下，太小了并行度不够；试了好几个大小，128x128 的 Block 效果比较好；

向量化计算是 Ascend C 的特色，一条指令处理一个向量；Vector 类型表示一组数据，长度是硬件相关的；Float16 的 Vector 长度是 128，一次处理 128 个 FP16 数据；标量循环改成向量操作，性能提升明显；

但向量化编程思维和标量不一样，习惯了 for 循环逐个元素处理；向量化要想成 batch 操作，Map、Reduce 这些模式；刚开始写得很别扭，经常写成标量风格，编译报错；

矩阵乘法的实现参考了 GEMM 的经典算法，分块、向量化、流水线并行；外层循环按 Block 分块，内层向量化计算；每个 Block 计算 C 的一小块，Cij = Sum(Aik * Bkj)；三层循环 i、j、k，k 是归约维度要累加；

数据重用优化做了很多工作，矩阵 A 的一行要重复用多次；从 GM 加载到 L1 后保持在 L1，多次使用；矩阵 B 的一列也是，缓存在 L1 减少访存；L0 Buffer 的使用更讲究，计算完立刻释放，给下一次计算腾空间；

流水线并排也是关键优化，数据加载、计算、结果写回三个阶段；用 Pipe 机制实现流水线，一个阶段在算，另一个阶段在取数据；Enque、Deque 接口管理 Pipe 队列，深度设成 2 或 3；Double Buffer 的思想，一块在算另一块在传输；

稀疏矩阵的处理加了压缩存储，CSR 格式存非零元素；遍历非零元素时用 values、row_ptr、col_idx 三个数组；判断元素是否为零，零就跳过不算；但条件分支在向量化里很难处理，SIMD 是所有通道执行同样指令；

Mask 机制解决了分支问题，向量操作可以带 Mask 参数；Mask 是个位向量，每一位对应一个元素；通过 Mask 选择性执行，实现条件操作；生成 Mask 的逻辑也是向量化的，Compare 指令比较生成；

原子操作也用上了，多个 Block 并行写同一个位置要同步；AtomicAdd 原子加法，保证累加正确；但原子操作慢，尽量减少使用；设计算法时让不同 Block 写不同位置，避免竞争；

性能分析工具用的 Msprof，类似 CUDA 的 nvprof；采集算子执行的时间线，看每个阶段耗时；发现瓶颈在数据搬运，GM 到 L1 的带宽没跑满；优化了数据排布，连续访问提高带宽利用率；

数据排布改成 ND2NZ 格式，适配 NPU 硬件；原来是 row-major 行主序，改成 fractal 分形排布；理解这个格式花了很久，看了好几遍文档；简单说是把矩阵分成 16x16 的小块，按特定顺序排列；这样硬件读取时缓存命中率高；

类型转换也踩坑了，输入是 FP32，计算用 FP16 精度；Cast 接口做类型转换，FP32 转 FP16；但精度损失要注意，数值范围超了会溢出；加了 Clamp 限制数值范围，再转换；结果转回 FP32 输出，保持接口一致；

量化计算也试了，INT8 量化能进一步提速；Scale 和 Offset 参数做量化和反量化；但量化后精度掉得比较多，mIoU 降了 2 个点；权衡性能和精度，最后还是用 FP16；

指令调度优化也做了，手动排列指令顺序；访存指令和计算指令交错，隐藏延迟；编译器的自动优化不够好，手动调度效果更好；但这个太底层了，写起来很累，像写汇编；

寄存器分配也要注意，L0 Buffer 的寄存器数量有限；一个核函数同时用的寄存器不能太多；超了编译时报错 register spill，寄存器溢出；减少临时变量，复用 Vector 对象；

边界处理是个细节坑，矩阵大小不一定是 Block 大小的整数倍；最后一个 Block 可能只处理部分数据；判断边界，用 Mask 控制只处理有效部分；不然会访问越界，段错误；

算子融合也研究了，把多个小算子合成一个大算子；减少中间数据的访存，提升整体性能；比如 MatMul + BiasAdd + ReLU 三个操作融合；在 MatMul 核函数里加 Bias 和激活，一次搞定；但融合后代码复杂度高，调试困难；

编译优化选项试了很多，-O3、-ffast-math、-march=native；有些选项能加速，有些反而变慢；一个个试，找最优组合；-ffast-math 对浮点优化激进，精度略有损失；

算子注册到 PyTorch 框架费了些功夫，写 Python 的 wrapper；torch.ops.load_library 加载算子库；自定义 autograd.Function 包装前向后向；反向传播也要写，矩阵乘法的梯度计算；dL/dA = dL/dC * B^T，dL/dB = A^T * dL/dC；

单元测试写了一堆，对比 PyTorch 原生算子的结果；随机生成输入矩阵，跑自定义算子和原生算子；逐元素对比，误差在 1e-3 以内算通过；边界情况也要测，空矩阵、单行单列、超大矩阵；

性能测试终于到了激动人心的环节，对比原生 matmul；稠密矩阵的情况，自定义算子略快 5%，没啥优势；稀疏矩阵 90% 零元素，自定义算子快 2.5 倍；稀疏度更高 95%，快 4 倍，符合预期；

功耗测试也做了，npu-smi 查看功耗；自定义算子功耗稍低，计算量少了功耗自然低；温度也低一些，70 度 vs 75 度；

精度验证跑了端到端的模型，推荐系统整体 AUC；自定义算子的模型和原生算子一致，精度没损失；误差在统计噪声范围内，可以放心使用；

部署上线打包成 wheel，pip install 安装；服务器上装好 CANN 环境，import 能正常加载；线上跑了一周，稳定性没问题；偶尔有个别 case 超时，加了个 fallback，超时自动降级到原生算子；

文档这块 Ascend C 的官方文档写得不够详细；很多 API 只有函数签名，没有用法说明；示例代码也少，要自己摸索；社区论坛问问题回复很慢，提 issue 也没人理；主要靠看源码和试错；

版本兼容性也是坑CANN 7.0 和 6.3 的 API 有差异；升级 CANN 后算子编译报错，部分接口废弃了；查 changelog 找替代接口，改了十几处才适配；

错误信息太隐晦，运行时报 error code 500036；查文档说是内存越界，但不知道哪里越界；加 printf 一点点排查，最后发现是 Block 大小算错了；

学习曲线陡峭，从零到能写算子要一个月；CUDA 背景有帮助，很多概念类似；但 Ascend C 的编程模型还是有特色，要重新适应；向量化、Pipe、Tiling 这些要吃透；

成本收益算了下，开发耗时两个月，代码 2000 行；性能提升 2-4 倍，推理服务器数量能减半；成本节省一年几十万，开发投入值得；

后续优化还有空间，稀疏度不同可以动态选择算法；Block 大小也可以根据矩阵 shape 自适应；还想试试 Sparse Tensor Core，硬件加速稀疏计算；

其他算子也想用 Ascend C 写，LayerNorm、GroupNorm 这些；积累算子库，后续项目能复用；团队也在学习，准备培训分享经验；

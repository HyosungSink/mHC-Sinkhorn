来一次分析之旅 关键词：Ascend C / CANN / Tiling / Double Buffer / 多核并行 / msProf 环境：Atlas 800T A2 训练服务器（昇腾 910B），CANN 8.0.RC3，Kernel 直调工程 一、一个让人尴尬的事实：能跑通 ≠ 能用 写过 Ascend C 算子的人大概都经历过这个瞬间：照着官方 add_custom 样例改一改，bash run.sh 一把过，精度比对 PASS，心里刚有点成就感——然后拿 msProf 一测，发现这个算子的等效访存带宽只有 20 多 GB/s。 而昇腾 910B 的 HBM 理论带宽是 1.1 TB/s 量级。 也就是说，算子"跑通"这件事，只解决了不到 3% 的问题。剩下 97% 全在怎么把数据高效地喂进 AI Core。这篇文章就用 Add 这个最简单的算子做载体，把从"能跑"到"打满带宽"中间的四步优化拆开讲清楚：Tiling → 多核切分 → Double Buffer → 对齐与融合。 选 Add 不是因为它有用，而是因为它足够"干净"——没有复杂的数学逻辑干扰，所有性能差异都来自数据搬运策略本身。这套方法论换到 LayerNorm、Softmax、RoPE 上是完全一样的。 二、先算上限：不做 Roofline 分析的优化都是瞎调 在动手改代码之前，必须先回答一个问题：这个算子的性能天花板在哪？ Add 算子 fp16，逐元素计算 z = x + y： ●访存：读 x（2 B）+ 读 y（2 B）+ 写 z（2 B）= 6 B / 元素 ●计算：1 次加法 = 1 FLOP / 元素 ●计算强度（Arithmetic Intensity）= 1 / 6 ≈ 0.17 FLOP/B 而 910B 的 fp16 向量算力与 HBM 带宽之比，量级在 100 FLOP/B 以上。0.17 远远落在 Roofline 曲线的斜坡段——这是一个彻底的 memory-bound 算子。 结论非常明确：任何试图优化"计算"的努力都是无效的，唯一的优化方向就是让 MTE（存储搬运单元）始终处于满载状态。 顺手把理论耗时算出来，作为后面所有版本的标尺。取 totalLength = 8 M（8388608 个 fp16 元素）：数据总量 = 8388608 × 6 B ≈ 50.3 MB 若有效带宽取 700 GB/s（HBM 实测可达带宽通常是理论值的 60%~70%） 理论耗时 ≈ 50.3 MB / 700 GB/s ≈ 72 µs  72 µs 就是这个算子的靶心。 有了这个数，后面每一版优化好不好，一眼就能判断。 这一步千万别省。我见过太多人上手就开始调 tileNum，调了两天从 500 µs 优化到 400 µs，很有成就感——却不知道理论下限是 72 µs，真正的问题在别处。Roofline 分析花十分钟，能省两天。 三、动手前：Kernel 直调工程与 CPU 孪生调试 调性能之前先把调试链路搭对，否则后面每改一版都要上板，迭代成本极高。 Kernel 直调（Kernel Launch）工程是做算子性能实验最轻量的形态，不需要写算子原型注册、不需要走 GE 图，一个 .cpp 写 kernel、一个 .cpp 写 host 侧调用就能跑：add_custom/ ├── add_custom.cpp      # kernel 实现（__global__ __aicore__ 函数） ├── main.cpp            # host 侧：申请内存、拷入、下发、拷出、比对 ├── data_utils.h ├── CMakeLists.txt └── run.sh              # 一键切换 CPU / NPU 模式  关键是它的双模式编译能力。同一份 kernel 代码，可以编成两个产物： ●CPU 孪生模式（-DASCENDC_CPU_DEBUG）：kernel 在 CPU 上以多线程模拟多核执行，可以用 gdb 单步、可以打印 LocalTensor 内容、可以直接看内存越界。逻辑和精度问题全部在这一步解决。 ●NPU 模式：真实上板，只用来测性能。 正确的工作流是：CPU 孪生跑通精度 → 上板测性能 → msProf 定位瓶颈 → 改代码 → 回到 CPU 孪生验证精度没崩 → 再上板。把精度问题和性能问题分开解决，是能否高效迭代的分水岭。反过来，如果你在板上一边查结果不对一边查为什么慢，基本等于同时解两个方程。 四、V1：Tiling —— UB 只有 192 KB，数据必须切 第一个绕不过去的硬约束：Unified Buffer（UB）容量。 910B 的每个 AIV 子核只有 192 KB UB。而我们要处理 50 MB 数据。所以不可能"一次搬完再算"，必须切块（Tiling），做成"搬一块、算一块、写一块"的循环。 UB 预算的算式其实很简单，记住它能省掉一半的调试时间：BUFFER_NUM × (输入个数 + 输出个数) × tileLength × sizeof(dtype) ≤ UB_SIZE - 预留  Add 算子有 2 输入 1 输出，V1 阶段先不开 Double Buffer（BUFFER_NUM = 1）：1 × 3 × tileLength × 2 B ≤ 192 KB  →  tileLength ≤ 32768  取 tileLength = 8192（16 KB / buffer，共占 48 KB，留足余量给编译器和栈）。 V1 版本的核心代码结构，采用 Ascend C 标准的三段式编程范式：#include "kernel_operator.h"  constexpr int32_t BUFFER_NUM = 1;   // V1：先不开 Double Buffer  class KernelAdd { public:     __aicore__ inline 是可以的，但除非你在做极致调优，否则没必要——TQue 生成的同步几乎总是正确且够快的。 V1 跑出来是 2000 µs 量级，离 72 µs 的靶心差了近 30 倍。原因很直白：我们只用了 1 个核。 五、V2：多核切分 —— 把 40 个 AIV 全用起来 昇腾的 AI Core 从 910B 开始是 AIC（Cube）+ AIV（Vector）双子核架构，向量算子跑在 AIV 上。910B 一张卡有 20 个 AI Core，对应 40 个 AIV。V1 只跑 1 个核，等于 97.5% 的搬运能力在闲置。 多核化在 Ascend C 里的写法非常轻量——不需要写任何"并行"逻辑，只需要让每个核处理自己那一段偏移：__aicore__ inline void Init(GM_ADDR x, GM_ADDR y, GM_ADDR z, tileNum / BUFFER_NUM;      // 关键：用 GetBlockIdx() 算出本核的 GM 起始偏移     uint32_t offset = this->blockLength * AscendC::GetBlockIdx();     xGm.SetGlobalBuffer((__gm__ half *)x + offset, this->blockLength); ascendcPlatform->GetCoreNumAiv();  尾块问题：如果 totalLength 不能被核数整除，直接整除会丢数据。生产级算子的标准做法是在 Tiling 结构体里下发两组参数——formerNum 个核处理 formerLength，tailNum 个核处理 tailLength，kernel 里根据 GetBlockIdx() 判断走哪个分支。这一步在样例代码里经常被省略，但它是从"demo"变成"能上线"的分界线。 V2 之后耗时降到 130 µs 左右，等效带宽约 390 GB/s。已经进入合理区间，但还差最后一层。 顺手说一句：多核化之后 blockDim 不宜盲目开到最大。对数据量很小的算子，核间的下发和同步开销可能超过并行收益，此时反而应该少开核。判断标准还是那句话——单核的 loopCount 至少要够填满流水（经验上 ≥ 8）。 六、V3：Double Buffer —— 让搬运和计算真正重叠起来 V2 的问题藏在 Process() 的循环里。当 BUFFER_NUM = 1 时，时序是完全串行的：CopyIn(0) → Compute(0) → CopyOut(0) → CopyIn(1) → Compute(1) → CopyOut(1) → ...    MTE2        VECTOR        MTE3        MTE2  ...  MTE2 在搬第 0 块的时候，Vector 单元在等；Vector 在算的时候，MTE2 又在等。三个硬件单元轮流干活，任意时刻只有 1/3 的硬件在工作。 Double Buffer 的思路就是把每个 Queue 开两份 buffer，让第 i+1 块的搬运和第 i 块的计算并行发生：时刻:    t0        t1        t2        t3        t4 MTE2:  CopyIn0   CopyIn1   CopyIn2   CopyIn3 VEC:             Compute0  Compute1  Compute2  Compute3 MTE3:                      CopyOut0  CopyOut1  CopyOut2  流水填满之后，三个单元同时工作，理论上可以逼近 单个瓶颈单元的耗时（对 memory-bound 算子就是 MTE 的耗时）。 改动只有两行：constexpr int32_t BUFFER_NUM = 2;   // ← 就这一处  // InitBuffer 的第二个参数即 buffer 数量，传 2 就开启了 Double Buffer pipe.InitBuffer(inQueueX,  BUFFER_NUM, this->tileLength * sizeof(half));  但有个坑必须注意：BUFFER_NUM 从 1 变 2，UB 占用直接翻倍。所以 tileLength 的算式里必须同步除以 BUFFER_NUM：this->tileLength = this->blockLength / tileNum / BUFFER_NUM;  这也是为什么前面代码里一直带着这个看起来多余的 / BUFFER_NUM。忘记这一步的典型症状是运行时报 UB 越界，或者更恶劣——静默的结果错误。 tileLength 到底取多少？这里有个经验区间：单次 DataCopy 的数据量落在 8 KB ~ 32 KB 比较理想。太小，MTE 指令的发射开销占比上升，搬运效率下降；太大，UB 装不下，且流水段数变少（loopCount 太小时流水根本填不满，Double Buffer 收益趋近于 0）。按 8 Mi 元素、blockDim = 32、tileNum = 16、BUFFER_NUM = 2 算：blockLength = 8388608 / 32 = 262144 tileLength  = 262144 / 16 / 2 = 8192        → 8192 % 16 == 0  ✓ 32 B 对齐 单次搬运量  = 8192 × 2 B = 16 KB             ✓ 落在 8~32 KB 经验区间 UB 占用     = 2 × 3 × 16 KB = 96 KB         ✓ 为 192 KB 的一半，余量充足 loopCount   = 16 × 2 = 32                   ✓ 段数足够，流水能填满  这里刻意选了 blockDim = 32 让所有数字整除，方便演示。实际用 GetCoreNumAiv() 拿到 40 时，8388608 / 40 = 209715.2 不整除——这就是上一节说的尾块场景，必须走 formerNum / tailNum 双分支。 V3 之后耗时约 80 µs，等效带宽 630 GB/s 量级。Double Buffer 单独贡献了约 1.6 倍加速，而代码只改了一个常量——这大概是 Ascend C 里性价比最高的一次优化。 七、V4：抠细节 —— 对齐、非对齐尾块、UB 内融合 最后这一层收益不大（80 → 72 µs 左右），但对做通用算子的人来说是必修课。 1. 32 B 对齐是硬要求 DataCopy 的搬运粒度是 32 B（一个 datablock）。如果 tileLength × sizeof(dtype) 不是 32 B 的整数倍，多出来的部分会被按整块搬运，把邻居的数据一起搬进 UB，或者把脏数据写回 GM。对 fp16 来说，tileLength 必须是 16 的整数倍。 更进一步，为了让 MTE 达到峰值效率，建议按 512 B（cacheline） 对齐。 2. 非对齐数据用 DataCopyPad 真实业务里 shape 不可能总是对齐的。这时候不要自己写 if-else 补齐，用 DataCopyPad + DataCopyExtParams，让硬件帮你处理尾部：AscendC::DataCopyExtParams copyParams{     1,                                          // blockCount     static_cast(tailLength * sizeof(half)),  // blockLen（字节数，可非对齐）     0, 0, 0                                     // srcStride / dstStride / rsv }; AscendC::DataCopyPadExtParams padParams{false, 0, 0, 0}; AscendC::DataCopyPad(xLocal, xGm[offset], copyParams, padParams);  3. 多算子融合到 UB 内完成 这是收益最大的"细节"。假设你的网络里有连续的 Add → Mul → Relu，如果作为三个独立算子调用，数据要在 GM 和 UB 之间往返 3 次（6 次搬运）。融合成一个 Ascend C 算子后，中间结果全程留在 UB 里，只需要开头搬入、结尾搬出各一次：__aicore__ inline void Compute(int32_t progress) {     auto xLocal = inQueueX.DeQue();     auto yLocal = inQueueY.DeQue();     auto zLocal = outQueueZ.AllocTensor();      AscendC::Add(zLocal, xLocal, yLocal, tileLength);   // 中间结果留在 UB     AscendC::Mul(zLocal, zLocal, xLocal, tileLength);   // 原地复用，零搬运     AscendC::Relu(zLocal, zLocal, tileLength);      outQueueZ.EnQue(zLocal);     inQueueX.FreeTensor(xLocal);     inQueueY.FreeTensor(yLocal); }  对 memory-bound 算子，融合带来的加速几乎是线性的——省掉多少次 GM 往返，就省掉多少时间。这也是 CANN 里各种 FusedAddRmsNorm、AddLayerNorm 存在的根本原因。 4. 别在 kernel 里做标量运算 GetBlockIdx() 之外的除法、取模、条件判断，能挪到 Host 侧 Tiling 里就挪走。Scalar 单元的运算会阻塞指令流水，msProf 里表现为 scalar_time 异常高。Tiling 结构体是免费的，kernel 里的每一次整数除法都不是。 八、用 msProf 判断"还能不能再快" 优化到某一步，怎么知道该收手了？看 msProf 的流水占比。 Kernel 直调场景下采集：msprof op --output=./prof_result ./add_custom_npu  重点看这几个字段： 字段 含义 怎么读 aiv_time(us) AIV 总耗时 算子的实际墙钟时间 aiv_mte2_time ●vec_ratio 接近 1 → 恭喜，你的算子是 compute-bound 的，优化方向完全不同（该去看 API 选择、数据类型、Cube 单元利用了）。 举个实际读数的例子。假设 V2（未开 Double Buffer）测出来是这样：aiv_time        = 130 µs aiv_mte2_time   =  78 µs   (60%) aiv_vec_time    =  22 2.tileLength 不是 32 B 对齐 → 精度比对偶发失败，且失败位置总在每块的尾部。 3.totalLength 不能被核数整除 → 尾核丢数据。上线前必须补 formerNum / tailNum 双分支。 4.Host 侧 Tiling 结构体和 kernel 侧定义不一致 → 参数错位、内存越界。用同一个 .h 头文件被两边 include，别手抄。 5.blockDim 写死成 8 或 20 → 换芯片型号立刻退化。始终用 GetCoreNumAiv() 查询。 6.tileNum 拍脑袋定 → 太大则单次搬运碎片化，太小则流水填不满。以"单次搬运 8~32 KB"反推。 7.先上板调试 → 应该先用 CPU 孪生调试（ASCENDC_CPU_DEBUG）跑通逻辑和精度，再上板调性能。上板阶段只解决性能问题，效率高得多。 8.用 printf 调试 → kernel 里用 AscendC::PRINTF 和 DumpTensor，并且记得在性能测试版本里去掉——它们本身会拖慢流水。 十一、小结 回头看，这四步优化背后其实只有一条主线：Ascend C 的性能优化，本质是在 192 KB 的 UB 这个狭窄窗口里，设计一条让 MTE 和 Vector 单元永不空闲的数据流水线。 ●Tiling 决定了数据能不能进 UB； ●多核切分 决定了有多少条流水线在同时跑； ●Double Buffer 决定了每条流水线的空转率； ●对齐与融合 决定了流水线里有多少无用搬运。 而 Roofline 分析和 msProf，是这条链路上的"始"与"终"——开工前算清楚天花板在哪，收工时确认自己贴到了天花板。少了这两步，优化就变成了碰运气。 Add 算子的结论换到 LayerNorm、Softmax、RoPE、Paged Attention 的 KV 搬运上，方法论一模一样。区别只在于：这些算子的 UB 预算里要多算几块中间 buffer，以及有些算子（比如带 reduce 的）需要额外考虑核间同步。但那是另一篇文章的内容了。 参考资料 ●Ascend C 算子性能优化实用技巧 01——流水优化 · 昇腾社区 ●Ascend C 算子性能优化实用技巧 05——API 使用优化 · 昇腾社区 ●快速入门-算子开发（基础篇） · CANN 开发文档

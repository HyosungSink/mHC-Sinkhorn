# 一次常见的算子性能陷阱：计算不多，数据却搬了很多次

- topicId: 02200222343129696347
- source: https://www.hiascend.com/developer/blog/details/02200222343129696347
- section: Ascend C
- createTime: 20260817095850

写高性能算子时，人很容易把注意力放到“计算”两个字上。 比如看到这样的代码： Mul(...) Add(...) Exp(...) 我们会自然地开始思考： 能不能少执行一次 Add？ 能不能把两个计算融合？ 有没有更快的 API？ 但对于不少算子而言，真正值得首先检查的并不是计算，而是： 同一份数据到底被搬了多少次？ 一、一次简单计算背后的成本 考虑一个简单流程： z = x + y 表面只有一次加法。 但从数据流角度看： 读取 x 读取 y ↓ 搬到片上 ↓ 执行 Add ↓ 结果写回 从整个过程来看，Add 只是其中一个环节。 如果算子的计算强度本身很低，那么数据搬运就可能占据很重要的位置。 这时候优化一两条计算指令，收益可能非常有限。 二、一个典型的问题：反复搬同一份数据 假设某个中间数据会参与三个步骤。 一种直接写法可能形成： GM → Local → Compute A → GM ↓ GM → Local → Compute B → GM ↓ GM → Local → Compute C → GM 从程序逻辑上完全正确。 但是同一份中间结果不断： 写回 Global Memory 再从 Global Memory 读回来 这意味着额外的数据流动。 如果中间结果实际上可以在片上继续被下一个阶段消费，那么就值得思考是否能够调整数据生命周期： GM ↓ Local ↓ Compute A ↓ Compute B ↓ Compute C ↓ GM 这也是算子融合能够提升性能的重要思想之一：减少不必要的中间数据落地。 三、小块搬运同样值得警惕 另一个常见情况是： 总数据很多 但是每次只搬一点点 例如： DataCopy 1 KB DataCopy 1 KB DataCopy 1 KB DataCopy 1 KB …… 相比合理地扩大连续搬运规模，大量碎片化的数据搬运往往会带来更多固定开销。 所以设计 Tile 时，不仅要问： “这块数据放得下吗？” 还应该问： “这个搬运粒度合理吗？” 四、内存对齐也不仅仅是“代码规范” 在普通程序里，对齐问题有时很容易被当作一种底层细节。 但在高性能算子里，地址布局可能直接影响数据访问效率。 因此设计 Tensor 布局和 Tiling 时，可以提前考虑： 起始地址 数据长度 连续访问 对齐要求 而不是等 Kernel 全部写完以后才处理这些问题。 官方的 Ascend C 搬运优化建议中也明确包含尽量使用较大的数据块、关注 GM 地址对齐以及合理选择搬运 API 等方向。 五、优化数据生命周期 我认为一个很实用的方法，是给算子画一张简化的数据流图。 例如： Input A ──┐ ├→ Compute 1 → Temp → Compute 2 → Output Input B ──┘ 然后针对每个箭头问三个问题： 1.数据现在在哪里？ 2.为什么必须搬到另一个位置？ 3.搬过去以后还会不会再次使用？ 如果第三个问题答案是“马上还要使用”，就值得检查是否存在不必要的往返搬运。 六、不要把 Local Memory 当成越大越好的缓存 当然，减少搬运也不是说： 所有中间结果全部留在 Local Memory。 Local Memory 本身是有限资源。 保留的数据越多，留给 Double Buffer、临时 Tensor 以及其他输入输出的空间就越少。 所以真正的问题仍然是一个资源权衡： 减少GM访问 ↕ 控制Local Memory占用 这也是算子优化有意思的地方。 很多时候不是简单地“消灭某一种开销”，而是在不同硬件资源之间寻找更加合理的平衡。 七、性能优化可以先画数据流，再看计算式 对于计算密集型算子，计算单元的利用率当然非常重要。 但对于许多 Element-wise、数据变换以及轻量计算算子，我认为一个很值得养成的习惯是： 在分析公式以前，先画一次数据到底怎么流动。 有时候一张简单的数据流图，就能发现代码里那些隐藏得很深的： 重复读取 重复写回 碎片搬运 不合理中间结果 而这些问题，往往比减少一条普通计算指令更值得优先处理。

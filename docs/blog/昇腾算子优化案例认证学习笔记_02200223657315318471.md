开篇：我为什么把“算子”看成一条流水线 以前我容易把算子理解为一个数学公式：输入张量经过几次运算得到输出张量。学习认证内容后，我发现真正决定 NPU 性能的往往是公式之外的部分：数据从哪里来、由哪个计算单元处理、什么时候可以开始下一块搬运、不同核之间是否互相等待，以及算子最终能不能被模型正确调用。 因此，这篇笔记不按课程目录逐章摘抄，而是沿着一个具体问题复盘：假设要实现一个“矩阵乘后接向量激活”的算子，如何从需求分析走到性能调优？这个过程几乎会遇到认证页面列出的所有知识点。 1. 需求分析：先回答四个问题 问题一：计算属于哪种类型？ 矩阵乘部分具有规则的二维数据复用，适合 Cube；激活函数通常是逐元素计算，适合 Vector。若把两部分完全放在一个单元上，可能出现某个单元忙、另一个单元闲置的情况，所以更自然的思路是采用 MIX，让 AIC 处理矩阵主计算，AIV 负责向量后处理。 问题二：数据规模是否值得分块？ 当 M、N、K 较大时，分块可以让 A、B 的 Tile 在片上重复利用；当矩阵很小，过度分块反而会被核启动和搬运开销抵消。BlockDim 也不能机械设置成最大值，应让每个 Block 都有足够工作量，并尽量减少尾块。 问题三：精度和数据类型是什么？ FP16/BF16 等低精度类型通常拥有更高吞吐，FP32 更有利于累加精度。选择数据类型时需要同时考虑模型容忍度、硬件指令支持、带宽和中间结果范围。精度要求高时，可以采用低精度输入配合更高精度累加，并在单算子和端到端两层进行验证。 问题四：这个算子如何接入模型？ 除了 Kernel，还要准备算子定义、输入输出描述、属性、Shape 推导、Tiling 信息、编译产物和注册信息。模型迁移时还需要确认框架调用的算子名字、参数顺序和默认行为完全一致，否则“Kernel 正确”并不等于“模型可用”。 2. 硬件视角：一次计算到底经过了什么 可以把一次 Tile 处理抽象成下面这条路径：HBM/Global Memory         │  MTE 搬运         ▼ 片上缓存（L2/片上 Buffer）         │  Queue 管理生产与消费         ▼ Cube 或 Vector 计算单元         │  双缓冲隐藏等待         ▼ 结果 Buffer ──MTE──> 输出内存 这个图里有三个容易忽略的事实： 1.计算单元通常不直接“随意”读取外部内存，而是等待数据搬到合适的片上位置； 2.Queue 同时承担内存复用和同步语义，Buffer 的所有权必须清晰； 3.只要搬运和计算不能重叠，理论峰值算力就很难转化为实际性能。 昇腾 AI 处理器的 AI Core、AI CPU、控制单元和 MTE 各有职责。分离耦合架构让它们能够并发，但也要求开发者明确任务边界。CANN 五层体系则把硬件能力逐步封装成运行时、算子库、编译和框架接口，算子开发者实际上是在这条软件栈上补充新的高性能实现。 3. Kernel 设计：从串行伪代码到 SPMD 3.1 串行逻辑 最初的算法可以写成：for each output tile:     load A tile and B tile     C tile = A tile × B tile     C tile = activation(C tile)     store C tile 3.2 并行化思路 使用 SPMD 后，每个 Block 负责一个或多个输出 Tile，通过 block_idx 计算自己的 M/N 起点。K 维可以在 Block 内循环累加，M/N 维则负责把不同输出区域分给不同 Block。这样做的关键不是“把循环拆开”这么简单，还要保证： ●各 Block 的数据量大致均衡； ●A、B Tile 的读取尽量连续； ●相邻 Block 不会频繁争抢同一缓存行； ●尾块有清晰的有效元素掩码。 3.3 流水化 单缓冲流程是“搬运—计算—搬运—计算”，每一步都可能等待。双缓冲后可以变成：时间轴:  T0        T1        T2        T3 Buffer0: 搬运A0B0  计算0     搬运A2B2  计算2 Buffer1:           搬运A1B1  计算1     搬运A3B3 只要搬运和计算资源相互独立，就能把部分延迟藏在计算时间里。但双缓冲会增加片上内存占用，因此必须结合 Tile 大小共同设计。 4. Vector、Cube、MIX：怎样做选择 Vector 路径 Vector 适合加法、乘法、比较、激活、归一化和规整归约。它的优势是编程灵活、适用面广；风险是如果每个元素都要从外部内存独立读取，带宽会成为主要瓶颈。 Cube 路径 Cube 适合 GEMM 和矩阵块运算，重点在于矩阵布局、分块尺寸、K 维累加和数据对齐。Cube 并不是“只要调用矩阵指令就快”，若 M/N/K 形状不合适、Padding 太多或 L1 重载严重，实际收益可能很低。 MIX 路径 MIX 把 AIC 与 AIV 结合起来：AIC 负责高密度矩阵计算，AIV 负责解包、量化、激活或其他向量后处理。设计 MIX 时要先划清两类任务的边界，再处理跨单元同步和中间 Buffer 生命周期。同步点越多，协同收益越容易被抵消。 GEMV 是一个很好的反例：小矩阵或向量长度较短时，AIV 方案可能因为启动和布局转换更轻而占优；规模足够大、矩阵复用充分时，AIC 方案才可能体现吞吐优势。最终选择必须由形状和 Profile 结果决定。 5. CATLASS 与模板化思维 如果每种矩阵形状都重新写一份底层代码，维护成本会迅速上升。CATLASS 通过模板参数表达数据类型、布局、Tile 形状和执行策略，把通用逻辑与硬件特化分开。其分层 Block 复用方式让我认识到：模板库不是“封装好的黑盒”，而是一组可以组合和替换的积木。 使用模板库时我会重点检查三件事： 1.默认 Tile 是否满足当前 M/N/K 形状和对齐条件； 2.模板支持的数据类型是否覆盖模型真实输入； 3.模板的搬运和同步策略是否与当前算子后处理阶段匹配。 模板化带来的可复用性很重要，但性能仍需用真实设备数据确认，不能因为代码更短就认定一定更快。 6. 算子注册与模型迁移：工程闭环不能缺席 模型从 PyTorch 等框架迁移到昇腾 NPU 时，我会先列一张算子清单，标记每个算子属于“已有实现、可自动替换、需要工具辅助、必须手工实现”中的哪一种。自动迁移适合标准接口；工具迁移适合批量扫描和生成修改建议；手工迁移适合特殊算子、动态控制流和精度敏感算子。 自定义算子接入至少包括以下核对项： ●算子名称和命名空间是否与框架调用一致； ●输入、输出、属性的顺序和类型是否一致； ●Shape 推导和动态 Shape 行为是否正确； ●Tiling 参数是否在 Host 和 Kernel 两侧使用同一含义； ●编译生成的二进制是否被正确注册和加载； ●部署环境中的 CANN、驱动和算子包版本是否匹配。 很多“运行时找不到算子”的问题并非算法错误，而是注册链路、包路径或版本不一致导致的，因此工程检查和代码检查同等重要。 7. 精度调试：先定位误差，再决定是否优化 我会采用三级对比法： 第一级：输入和中间数据 确认 Host 到 Device 的数据类型、布局、stride 和 Padding 没有发生变化。尤其要警惕未初始化 Padding 区参与计算，以及尾块读取超出有效范围。 第二级：单算子输出 用 CPU 或高精度参考实现生成 Golden，比较最大绝对误差、平均绝对误差和相对误差。对于指数、除法、归一化等数值敏感操作，还要关注输入范围和溢出。 第三级：端到端结果 单算子误差可接受，不代表模型最终指标一定不受影响。应在模型层面对关键层、最终输出和业务指标进行验证，区分误差累积与算子单点误差。 只有在精度基线稳定后，才适合进行激进的低精度、融合或近似优化，否则很难判断性能变化是否伴随了正确性回退。 8. 性能分析：一次完整的 Profile 复盘 8.1 先看现象 如果 Kernel 耗时高，我先看是 Cube/Vector 利用率低，还是 MTE 带宽接近上限；如果总耗时不高但波形空泡明显，通常说明流水没有重叠；如果不同 Block 耗时差异大，则要怀疑分块或尾块负载不均。 8.2 再提假设 例如观察到搬运时间占比高，我会提出“连续搬运不足或 Tile 太小”的假设；观察到 Cube 等待数据，则提出“Buffer 深度不够或 MTE 与计算没有重叠”的假设。每次只改变一个变量，避免多个改动同时发生导致结论不清楚。 8.3 最后量化 使用 msprof 对比优化前后的 Kernel 时间、带宽、计算利用率、核占用和端到端延迟。仿真波形用来识别等待链和流水断点，真实设备 Profile 用来确认收益是否稳定。性能指标必须和输入 Shape、Batch、数据类型一起记录，否则不同测试条件下的数字没有可比性。 9. GEMM 和通用调优的经验清单 围绕 GEMM，我总结出以下顺序： 1.先选合适的 M/N/K 分块； 2.确保矩阵和搬运满足对齐要求； 3.用双缓冲减少搬运等待； 4.根据访问模式调整 Swizzle 和 Block 映射； 5.检查 Padding 带来的无效计算比例； 6.评估 Cube 与 Vector 的职责分配； 7.用 Profile 验证是计算瓶颈还是访存瓶颈。 通用算子也可以遵循同一逻辑：减少外部内存往返、提高片上复用、合并可融合的计算、控制同步数量、选择合适 API 和数据类型。所谓“四种映射策略”，本质上是在核、Tile、计算通道和访存路径之间做不同分配；改变映射后，必须重新检查带宽、缓存和负载均衡。 10. 认证复习计划与个人收获 我把复习内容分成“概念、代码、工具”三条线： ●概念线：处理器组件、CANN 五层体系、MTE、Queue、SPMD、CATLASS 和 HCCL； ●代码线：完成一个 Vector 算子、一个 GEMM 类算子和一个带后处理的混合算子； ●工具线：完成编译、注册、单元测试、精度对比、msprof 采集和结果记录。 最重要的收获是建立了闭环意识：性能优化不能脱离正确性，正确性也不能脱离部署链路；硬件架构知识只有落实到数据布局、Tile 和同步设计中，才会真正转化为算子性能。 结语 通过这次认证内容学习，我对 Ascend C 算子开发的理解从“会调用 API”推进到“能解释数据为什么这样流动、并能用工具验证优化是否有效”。后续如果继续深入，我会优先补齐 MIX 跨单元协同、CATLASS 高阶模板和复杂动态 Shape Tiling 三个方向，并将每次实验的 Shape、版本、精度和 Profile 数据一并记录，形成可复用的优化案例库。

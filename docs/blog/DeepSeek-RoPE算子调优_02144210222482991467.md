# 昇腾上DeepSeek模型的RoPE算子调优：一次替换带来的2倍加速

- topicId: 02144210222482991467
- source: https://www.hiascend.com/developer/blog/details/02144210222482991467
- section: Deepseek专区
- createTime: 20260330030803

去年年底，我们在昇腾Atlas 800上部署DeepSeek-V2模型，跑一个实时对话的Demo。模型跑起来了，但首字延迟（TTFT）始终在500毫秒以上，用户体验很差。我们用profiler一抓，发现了一个意想不到的瓶颈：RoPE（旋转位置编码）相关算子占了整整30%的推理时间。

RoPE是DeepSeek用来做位置编码的核心模块，每个Transformer层都要算一次。按理说这个算子计算量不大，不应该成为瓶颈。但它确实占了30%。

这就奇怪了。

### 第一回合：拆解RoPE

DeepSeek的RoPE实现分两步：先计算旋转矩阵的sin/cos值，再把Query和Key矩阵和旋转矩阵做逐元素乘法。在原始的PyTorch实现里，这两步都是几行代码的事：

```python
def apply_rotary_pos_emb(q, k, cos, sin):
    q_embed = (q * cos) + (rotate_half(q) * sin)
    k_embed = (k * cos) + (rotate_half(k) * sin)
    return q_embed, k_embed
```

昇腾的ATC工具在转换时，会把这几行代码映射成一系列昇腾算子：Mul、Add、Concat等。我拿到转换后的OM模型，用profiler逐层分析，发现这些看似简单的算子，在昇腾上执行时却问题很大。

问题出在“旋转”这一步。`rotate_half`操作在PyTorch里是通过切片和拼接实现的，昇腾编译器把它翻译成了多个Gather和Concat算子，而这些算子在昇腾上的执行效率并不高。更麻烦的是，这些操作涉及大量的内存重排，导致数据在片上缓存和DDR之间反复搬运，带宽压力很大。

### 第二回合：寻找替代方案

既然RoPE的“通用”实现在昇腾上效率不高，有没有更“昇腾友好”的实现方式？

我开始翻昇腾的算子库，看有没有专门为RoPE设计的算子。在CANN的`custom_op`目录下，我找到了一个叫`RotaryPositionEmbedding`的自定义算子。说明文档里写着：“对旋转位置编码进行融合优化，减少内存访问，适用于Transformer类模型。”

我如获至宝。这个算子的输入是q、k和位置编码表，输出直接就是旋转后的q、k。它把原来需要好几个算子完成的操作，融合成了单个算子，理论上可以减少内存访问和算子启动开销。

我立刻在模型转换时，把RoPE部分替换成这个自定义算子。昇腾的ATC支持通过配置文件指定算子的映射规则，我写了个`op_mapping.json`，告诉编译器：遇到`apply_rotary_pos_emb`这个子图，就用`RotaryPositionEmbedding`替代。

转换成功，重新部署，跑profiler。

RoPE相关算子的时间占比从30%降到了12%。首字延迟从520毫秒降到了380毫秒。效果立竿见影。

### 第三回合：还有优化空间

12%还是有点高。我继续看profiler数据，发现`RotaryPositionEmbedding`本身跑得很快，但它前后的数据格式转换算子（比如Transpose）却多了起来。

这是因为RoPE自定义算子的输入输出格式和模型其他部分不完全匹配。RoPE要求q、k的shape是[batch, seq_len, num_heads, head_dim]，而模型其他部分用的是[batch, num_heads, seq_len, head_dim]。每次RoPE前后都要做一次Transpose，这两次Transpose加起来又占了5%的时间。

能不能让整个模型统一用一种数据格式？我去看昇腾的文档，发现可以通过`--op_compiler_config`参数，告诉编译器“优先使用某种数据布局”。我设成`NHWC`（昇腾最友好的布局），然后重新转换整个模型。

这次RoPE前后的Transpose消失了，RoPE部分的耗时进一步降到了7%。首字延迟降到300毫秒。

### 第四回合：精度验证

性能上去了，精度不能掉。我跑了一组测试数据，对比替换前后的模型输出。余弦相似度在0.999以上，可以认为没有精度损失。

自定义算子的实现和PyTorch原版的数学逻辑是完全一致的，只是把多个操作融合在了一起。理论上不会有精度差异，但出于谨慎，我还是做了充分验证。

### 最终效果

从最初500毫秒的首字延迟，到最后300毫秒，提升了40%。其中RoPE算子优化贡献了主要的加速，数据布局调整又贡献了一部分。


| 优化阶段       | RoPE耗时占比 | 首字延迟 |
| -------------- | ------------ | -------- |
| 初始版本       | 30%          | 520ms    |
| 替换自定义算子 | 12%          | 380ms    |
| 统一数据布局   | 7%           | 300ms    |

### 复盘

这次优化让我学到几个关键点：

1. **不要小看“小算子”**。RoPE看起来只是几个乘加操作，但在硬件上执行时，数据布局、内存访问模式对性能影响巨大。一个算子如果被反复调用（每层一次），哪怕只优化一点点，累计收益也很可观。
2. **昇腾的自定义算子库是宝藏**。CANN里有很多现成的融合算子，专为常见模型结构优化，但文档分散，需要自己去翻。`RotaryPositionEmbedding`这个算子，如果我不去翻`custom_op`目录，可能永远不知道它的存在。
3. **数据布局要统一**。模型内部不同模块之间频繁的数据格式转换，会引入大量开销。尽量让整个模型使用同一种数据布局（昇腾上推荐NHWC），能减少很多无谓的Transpose。
4. **性能优化的优先级要明确**。我一开始盯着Attention、MLP这些大块头，结果RoPE这种“小透明”才是真瓶颈。profiler不会说谎，数据驱动优化比直觉靠谱。

### 后记

后来我把这套优化方案整理成了团队内部的“昇腾模型算子调优指南”，RoPE替换和数据布局统一成了标准步骤。之后每次部署新的DeepSeek模型，首字延迟都能稳定在300毫秒左右。

那台Atlas 800现在还在跑着那个实时对话Demo，每次看到首字几乎秒出，我都会想起那个翻`custom_op`目录的下午。有些算子的名字可能不起眼，但当你找到它、用上它，它可能就是你的性能加速器。

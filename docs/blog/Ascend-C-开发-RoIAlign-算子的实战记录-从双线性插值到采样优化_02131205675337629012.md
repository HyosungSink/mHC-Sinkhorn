# Ascend C 开发 RoIAlign 算子的实战记录，从双线性插值到采样优化的性能死磕之路；

九月份部署 Mask R-CNN 目标检测模型，整个推理流程中 RoI Pooling 层特别慢，成了性能卡点。模型要处理 1000 个候选框，每个框做 RoIAlign 提取 7x7 的特征，输入特征图是 [1, 256, 200, 200]。PyTorch 的 torchvision.ops.roi_align 在昇腾上性能很差，1000 个 RoI 要处理 35ms，比主干网络的推理还慢。而且这个算子只有 CPU 实现，昇腾平台没有 NPU 加速版本，数据要在 CPU 和 NPU 之间反复搬运，白白浪费时间。研究了一圈发现只能用 Ascend C 自己写，把 RoIAlign 搬到 NPU 上跑。听起来就是个池化加插值，实际开发时才发现坐标计算、采样策略、边界处理每个细节都是坑。从开始写到优化完用了快两个月，把浮点坐标处理、不规则内存访问、并行度设计的细节都摸透了。

需求这块先理清楚，RoIAlign 是 Mask R-CNN 提出的改进版 RoI Pooling，解决了 RoIPooling 的量化误差问题。输入是特征图 [C, H, W] 和 RoI 列表，每个 RoI 是 [x1, y1, x2, y2] 四个浮点坐标加上 batch_idx。输出是固定大小的特征 [num_rois, C, pooled_h, pooled_w]，通常 pooled_h = pooled_w = 7。RoIAlign 的核心操作是对每个 RoI，均匀划分成 pooled_h x pooled_w 个 bin，每个 bin 内采样 sampling_ratio x sampling_ratio 个点做双线性插值，最后取平均或最大值。关键点是坐标是浮点数，不做量化，保持精度。sampling_ratio 通常是 2，每个 bin 采样 4 个点。

开发环境用的 CANN 7.0.1，MindStudio 调试工具用得越来越顺了。Ascend C 的文档里没有 RoIAlign 的参考，只有基础的池化示例。参考了 MMDetection 的 CUDA 实现，但 CUDA 的线程模型和 Ascend C 不一样，要重新设计并行策略。PyTorch 的 C++ 实现看了源码，逻辑清楚但全是标量操作，性能不行。

第一版实现按照最直观的思路写，四层循环遍历 RoI、输出的 h、w、channel。对每个输出位置，计算对应的 bin 范围，然后在 bin 内采样。采样点的坐标是浮点数，要对周围 4 个整数坐标的像素做双线性插值。插值公式是 f(x,y) = (1-dx)(1-dy)f(i,j) + dx(1-dy)f(i+1,j) + (1-dx)dy f(i,j+1) + dx*dy*f(i+1,j+1)，其中 dx = x - floor(x)，dy = y - floor(y)。写了个双线性插值函数，输入是特征图和浮点坐标，输出是插值结果。

第一版跑起来性能惨不忍睹，1000 个 RoI 要 80ms，比 CPU 版本还慢一倍。全是标量操作，一个采样点一个采样点算，完全没用上向量化。而且每个采样点要访问特征图的 4 个位置，访存完全随机，Cache Miss 率极高。

坐标计算优化了下，RoI 的坐标要映射到特征图。输入图像可能做了下采样，特征图的 stride 要考虑进去。spatial_scale 参数表示特征图相对输入图的缩放比例，通常是 1/16 或 1/32。映射公式是 roi_start_w = x1 * spatial_scale，roi_end_w = x2 * spatial_scale。bin 的宽度是 bin_size_w = (roi_end_w - roi_start_w) / pooled_w。每个 bin 内采样点的坐标计算也很繁琐，要均匀分布。

采样策略研究了下，sampling_ratio 是超参数，可以设成固定值或自适应。固定值比如 2，每个 bin 采样 2x2=4 个点。自适应是根据 bin 的大小动态调整，bin_size 大就多采样，小就少采样。公式是 sampling_ratio = ceil(bin_size)，但要限制上下限，太多了计算量大，太少了精度差。测试了几个策略，固定 2 效果最稳定。

双线性插值的向量化特别难，每个采样点要访问 4 个位置，位置是浮点坐标算出来的，完全不规则。试了 Gather 指令，但一次只能 gather 一个向量，4 个位置要引用 4 次。而且 Gather 的索引是整数，浮点坐标要先 floor 再转整数。权重系数 dx、dy 也是浮点数，每个采样点都不一样，没法批量处理。

改了并行策略，不是按输出位置并行，而是按 RoI 并行。每个 RoI 分配一个 Block，多个 Block 并行处理多个 RoI。Block 内遍历输出的 h、w、c 和采样点，还是标量操作。但多个 RoI 能并行，利用了硬件的多核。测试了下性能提升到 50ms，但还是不够快。

特征图预加载到 L1 Buffer，减少 GM 访问。一个 channel 的特征图 200x200 个 FP32，160KB，L1 能放下。预加载后所有 RoI 共享，采样时从 L1 读取。但 RoI 访问的区域不同，不是所有 RoI 都需要整个特征图。改成按需加载，只加载 RoI 覆盖的区域加上 padding。这样 L1 能放下更多 channel，减少加载次数。

浮点坐标的处理踩了个坑，floor 函数在边界情况有问题。坐标是负数或超出范围时，floor 的结果要 clamp 到 [0, H-1] 和 [0, W-1]。不然访问越界，段错误。还有个坑是坐标刚好在整数位置，floor 后 dx=0 或 dy=0，插值退化成取单个像素。这种情况可以优化，不用算 4 个位置，只算 1 个或 2 个。

边界处理加了 padding，特征图边缘的像素外面补 0。采样点超出特征图范围时，插值用 0。但补 0 会影响平均值，改成重复边缘像素。最边缘的像素向外扩展，保持数值连续。这个策略和 OpenCV 的 BORDER_REPLICATE 一致。

pooling 类型支持了 avg 和 max 两种，avg 是对采样点取平均，max 是取最大值。avg 用的多，Mask R-CNN 默认用 avg。max 的实现简单点，不用累加只用比较。写了个模板函数，根据 pooling_mode 参数选择。

aligned 参数也加上了，控制坐标对齐方式。aligned=True 时，RoI 的坐标不做 -0.5 的偏移，直接用原始坐标。aligned=False 时，要减 0.5，这是为了兼容旧版本的实现。测试了两种模式，结果略有差异，但都在容忍范围内。

批量处理优化了下，1000 个 RoI 一次性处理太多，分成多个 batch。每个 batch 处理 100 个 RoI，batch 之间串行。batch 内的 RoI 并行，每个 RoI 一个 Block。这样内存占用可控，而且能更好地利用 L1 Cache。

向量化尝试了很多方法，最后在 channel 维做了向量化。一个 RoI 的输出是 [C, pooled_h, pooled_w]，C=256，可以向量化。一次处理 64 个 channel，用向量指令加载和存储。但采样和插值还是标量的，因为坐标不规则。向量化的收益有限，性能提升 20% 左右。

采样点的计算也优化了，bin 内的采样点坐标提前算好。对于 pooled_h=7, pooled_w=7, sampling_ratio=2 的配置，每个 RoI 有 7*7*2*2=196 个采样点。提前算好这 196 个采样点的相对坐标，存成表。运行时只需要乘以 bin_size 再加上 roi_start，不用每次都算。查表法省了很多计算，性能提升明显。

内存访问模式还是不理想，采样点访问特征图是随机的。试了预取，但预取的效果不好，因为不知道下一个采样点在哪。改用软件缓存，把访问过的像素缓存在 L0 Buffer。后续采样点如果访问相同位置，直接从缓存读。但缓存管理有开销，测试下来收益不大。

数值精度对比了 FP32 和 FP16，插值计算用 FP32 精度高。但输入特征图是 FP16，Cast 转换有开销。用了混合精度，输入 FP16，插值计算 FP32，输出 FP16。这样兼顾了性能和精度，误差在 1e-4 以内。

性能测试终于看到明显提升，优化后的 RoIAlign 从 80ms 降到 8.5ms，提升了 9 倍多。对比 CPU 版本的 35ms，快了 4 倍。不同 RoI 数量测试了几组，100 个 RoI 是 1.2ms，500 个是 4.5ms，1000 个是 8.5ms，基本线性增长。

不同 pooled_size 也测试了，7x7 是 8.5ms，14x14 是 22ms，输出越大计算量越大。sampling_ratio 的影响也测了，1 是 5ms，2 是 8.5ms，4 是 18ms，采样点越多越慢。

不同特征图大小也测了，[256, 100, 100] 是 4.2ms，[256, 200, 200] 是 8.5ms，[256, 400, 400] 是 25ms。特征图越大，采样时访存越慢。

功耗和温度监控了下，RoIAlign 算子的 NPU 利用率 45%，主要是内存密集型。功耗 9W，温度 58 度，散热没问题。

算子注册到 PyTorch 框架写了扩展，torchvision.ops.roi_align 的接口保持一致。输入是 features, boxes, output_size, spatial_scale, sampling_ratio, aligned 这些参数。boxes 是 [num_rois, 5] 的 Tensor，每行是 [batch_idx, x1, y1, x2, y2]。

梯度计算也写了，RoIAlign 的反向传播比较复杂。梯度要反向传播到 features 和 boxes 两个输入。features 的梯度是把输出梯度通过插值反向传播回去。boxes 的梯度一般不算，因为 boxes 是 proposal 网络的输出，单独训练。

单元测试写了几十个 case，各种 RoI 数量、各种参数组合都测到。对比 torchvision 的实现，逐元素验证误差在 1e-4 以内。还测试了边界情况，RoI 超出特征图、RoI 面积为 0、RoI 坐标反了，都要能正确处理。

实际部署在 Mask R-CNN 模型上，整个推理流程测试了端到端性能。推理时间从 180ms 降到 135ms，RoIAlign 不再是瓶颈。检测精度没有变化，mAP 和 PyTorch 一致。

FPN 多尺度特征也测试了，Mask R-CNN 有 5 个尺度的特征图。不同 RoI 根据面积选择不同尺度，每个尺度单独做 RoIAlign。写了个 wrapper 支持多尺度输入，根据 RoI 的面积分配到对应尺度。

多线程并发测试了 4 个线程，每个线程处理一张图。线程安全，Context 隔离。4 线程吞吐量是单线程的 3.5 倍，扩展性还行。

错误处理加了输入检查，RoI 坐标要合法，x1 < x2 且 y1 < y2。spatial_scale 要大于 0，pooled_size 要大于 0。batch_idx 不能超出范围。内存分配失败也捕获异常。

版本兼容性测试了 CANN 不同版本，7.0 和 6.3 接口一致。PyTorch 1.11、2.0 都能用。ONNX 导出有点麻烦，RoIAlign 在 ONNX 里是个算子，但参数不完全一样。写了个转换函数，把参数映射过去。

线上运行了三周，处理了几十万张图片，稳定性很好。没出现过错误输出，性能监控正常。偶尔有几次超时，都是输入图片超大导致的，RoI 数量超过预期。加了个上限检查，RoI 超过 2000 个就截断或报错。

性能对比记录了数据，CPU RoIAlign 35ms，自定义 NPU 8.5ms，提升 4.1 倍。端到端 Mask R-CNN 从 180ms 降到 135ms，FPS 从 5.6 提升到 7.4。实时性还不够，但比原来好多了。

成本收益算了下，开发两个月，代码 3800 行。性能提升 4 倍，检测服务吞吐量提升 30%。服务器数量能减少 25%，成本节省可观。而且 RoIAlign 在 Faster R-CNN、Cascade R-CNN 都能用，复用价值高。

后续优化还想试试，融合前面的 RoI Proposal 生成，一个算子完成 proposal 和 align。还想研究 Dynamic RoIAlign，根据 RoI 的大小动态调整采样策略。小 RoI 少采样，大 RoI 多采样，平衡精度和性能。

文档整理了完整的开发笔记，双线性插值的实现、坐标映射的公式、采样策略的选择都记录了。踩过的坑也写成了 FAQ，浮点坐标处理、边界情况、精度对齐这些细节。代码注释很详细，关键算法都解释了数学原理。

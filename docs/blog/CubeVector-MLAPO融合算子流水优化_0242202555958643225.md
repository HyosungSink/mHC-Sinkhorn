# 1、背景

> Cube/Vector融合是一种常见的算子融合场景， 由于Cube/Vector大融合算子涉及的步骤多，极容易漏优化空间，因此本文以MLAPO算子为例，总结了一套性能优化点排查思路，助力极致流水优化。
>
> MLA预处理Device计算耗时长，超小shape下较多算子头开销过半，单层40+算子形成Host Bound。其中15个算子执行耗时平均低于下发耗时，每个算子的头尾开销严重，其中非计算类（Split/Concat/Transpose）占比40%，整体性能距理论算力差3倍左右。
>
> 针对该算子场景，提出MLAPO大融合方案。首先实施VV融合策略，将KV侧（RmsNorm+Rope+ReshapeAndCache）和Q侧（Rope+Concat）分别融合，实现预处理阶段性能倍增。
> 然后将多级Cube/Vector算子深度融合进单一算子，尝试突破Host/Device协同优化、Cube/Vector融合优化极限。

# 2、优化分析与优化

完整算子流程分为五个阶段，串行执行：

# 格式优化

首先，涉及Cube计算的算子，格式优化转NZ是利用昇腾硬件亲和性的常见性能优化手段。

## 爱因斯坦乘NZ

ND格式是神经网络中最常见且最基本的张量存储格式，代表N维度的张量数据。为了在达芬奇架构中更高效的搬运和进行矩阵计算，引入一种特殊的数据分形格式，NZ格式。

![0d2ee559-a9c2-41d2-9693-94469b5b4340.png](cid:pic_2)

NZ格式，如下图所示，矩阵的数据格式为NW1H1H0W0。整个矩阵被分为（H1\*W1）个分形，按照column major排布，形状如N字形；每个分形内部有（H0\*W0）个 元素，按照row major排布，形状如z字形。其中，H0,W0表示一个分形的大小。

![c85537a4-984c-42a0-a504-d1bbe24c1ff1.png](cid:pic_3)

将ND格式转换为NZ格式，即对最低两维（一个Tensor的所有维度，右侧为低维，左侧为高维）进行Pad、拆分以及转置。例如 (..., B，M, N )->pad->(..., B, M1\*M0, N1\*N0)->reshape->(...,  B, M1, M0, N1, N0)->transpose->(..., B, N1, M1, M0, N0)

针对MLAPO算子，优化爱因斯坦乘的wuk格式支持NZ，即昇腾硬件亲和数据格式，从而降低算子的搬运开销，提升性能。

```cpp
template <DataFormat formatB, bool transB, uint32_t swizzleDirect, uint64_t splitGapA, uint64_t splitGapC>
__aicore__ __force_inline__ uint64_t PpMatmulEinSum<formatB, transB, swizzleDirect, splitGapA, splitGapC>::GetOffsetB(
    const uint64_t batchIdx, const uint64_t kIdx, const uint64_t nIdx)
{
    if constexpr (formatB == DataFormat::ND) {
        if constexpr (transB) {
            return batchIdx * k * n + nIdx * n0 * k + kIdx * k0;
        } else {
            return batchIdx * k * n + kIdx * k0 * n + nIdx * n0;
        }
    } else {
        if constexpr (transB) {
            return batchIdx * RoundUp<CONST_16>(n) * RoundUp<CONST_16>(k) + kIdx * k0 * RoundUp<CONST_16>(n) +
                   nIdx * n0 * CONST_16;
        } else {
            return batchIdx * RoundUp<CONST_16>(k) * RoundUp<CONST_16>(n) + nIdx * n0 * RoundUp<CONST_16>(k) +
                   kIdx * k0 * CONST_16;
        }
    }
}
```

注：此处实现是兼容性修改，根据模板参数formatB选择走ND还是NZ。

新增爱因斯坦乘NZ特性后，算子总体耗时明显减少，Cube利用率、Vector利用率和数据搬运效率均明显增加。

# CV间流水优化

## CV任务级并行

初始方案的计算流程3、4、5阶段抽出并行度，设计初就要根据阶段的预估耗时来实现。

![9b387aad-5ea5-440d-a189-ac8cd8b2937d.png](cid:pic_4)

注：虽然Cube侧的所有流水同步由AscnedC框架完成，但框架的自动实现策略过于激进，会影响算子性能。

![e4a948a7-eb81-46c7-84b2-b4fc7e7b19b6.png](cid:pic_5)

而MLAPO是CV大融合算子，同步信号跨Cube和Vector核进行核间通信，依赖较为复杂，因此MLAPO算子使用手动细化插入同步信号，以实现任务级颗粒度的Cube/Vector核间并行。

## CV间依赖最小化等待

CV之间非必要依赖不等待，不依赖的尽量先行，同步的时候可以通过不同的事件ID，解决无依赖数据的串行，减少不需要的依赖和等待可以提升流水并行度，从而提升性能。

针对MLAPO融合算子，优化前，cube核的MTE2依赖于vector核的计算和搬运，其流水图如下所示，其权重预取的MTE2的起始受阻于CV的核间同步信号，导致预取指令跟在vector核搬运完成后串行执行：
![056ad2de-4c04-4c3c-aec7-82cc8238ed07.png](cid:pic_6)

实际上，针对权重预取，cube和vector间的同步信号可以完全取消，并没有逻辑上的依赖，消除非必要的同步信号后，优化的流水如下图所示，可以实现CV核间的MTE2并行：

![d9b0f5fe-56e4-4ba6-a551-76209a78a3ed.png](cid:pic_7)

## CV间资源竞争（MTE2带宽）优化

需要重点关注：检测改动点是否让骨架流水线的耗时增大。

消除非必要同步信号后，算子的MTE2Bound可以做到最大程度的消除气泡，CV核间非必要不等待的部分可以实现MTE2并行，且没有牺牲MTE3，最大程度利用带宽，从而达到整体上的性能提升。

# CV内流水优化

## Preload技术

由于搬运或者计算队列有限，有时候MTE队列会收到标量计算/同步指令的影响，导致关键指令不能正常下发，被阻塞。可以采用Preload技术规避硬件的影响，不需要前置计算的要尽量先行，从而提升带宽占比。

权重预取：具体来说，针对Cube核上的Matmul计算，需要等vec的核间同步信号，核间的同步信号导致MTE2的额外等待开销。MTE2要提前放在核间同步WAIT前，同时为了迎合这个改动，后面的逻辑统一调整为了预取。因此需要对原有代码进行指令重排来实现指令预发射的动作。将第一次MTE2指令提出到循环外，并在循环内提前调用下一次MTE2指令，从而达到指令预发射的目的。我们将这种指令重排技术称为Preload技术。
![a3edc0b2-b489-4ba7-b046-1839b385558d.png](cid:pic_8)
针对MLAPO算子，可以在Matmul计算之前将权重矩阵预取到L1，见图中①和②的MTE2流水即为Preload预取，这样可以提升带宽，达到性能优化的目的。

## PingPong操作

PingPong操作：想让MTE2流水尽可能的掩盖其他流水的耗时，PingPong操作属于比较常规的优化手段，与开启Double Buffer指的是同一件事。

具体来说，由于后续流水线依赖于MTE2流水线，为了防止后续流水线等待时间过长，且能被MTE2流水线掩盖，需要进行Double Buffer设计，即为每个内存块开启2片内存。

在实现Double Buffer后再使用msprof op simulator工具进行仿真，可得到如下仿真波形图。开启PingPong操作后，权重预取就可以并行起来，流水占比会进一步提升，从而提升性能。

![243bba7d-9a52-4e1e-a44e-d2a783fbc7ca.png](cid:pic_9)

注意：虽然PingPong操作属于基础优化手段，但实际编码存在多个易被忽视的地方：

1、预取机制失效陷阱：仅对Ping缓冲区实施预取，导致Pong缓冲区数据加载延迟无法被计算掩盖。需建立严格的交替预取机制，在每次迭代开始时对下一缓冲区的数据进行预取，确保预取窗口覆盖完整的双缓冲周期。

2、避免重复计算：针对昇腾的存储排布特性，由于Ping/Pong缓冲区的swizzle模式是严格一致的，为了避免重复计算存储模式参数，可以实现双缓冲区的swizzle参数共享，即Ping/Pong预取可以合并起来，抽象成一个函数，不用计算两次swizzle。

## 局部初始化

在实现CV间流水优化，且增加Preload技术和PingPong操作后，发现虽然Cube核的第二个Preload满足优化预期并行度，但是第一个Preload下发依旧阻塞，串行后置于Vector核的MTE2，不满足预期并行度。

进一步分析流水发现在Cube核的Preload启动之前有很多scalar头开销，即在初始化部分有很多无关的标量，如下图所示：
![547df79a-55c6-4296-b34c-d4b7cb3d4e79.png](cid:pic_10)

通过局部初始化技巧，即只初始化Preload相关的scalar，计算完成后立即提前下发Preload的MTE2指令，将无关的scalar初始化后置，即可解决第一个Preload下发的阻塞问题，整体流水提前，达到性能提升的目的。

![e075499f-a1ce-4576-af4b-a89f561ef33a.png](cid:pic_11)

具体实践启示我们，可以通过调整关键指令的位置，降低scalar对流水的影响，进一步提升性能。具体来说，针对scalar在Cube/Vector融合类算子kernel内尽量不再要全部初始化，可以将scalar看作一个单独的流水线，此时做局部初始化，会有不错的性能收益。

综合上述性能优化手段，最终单算子平均性能提升10%。

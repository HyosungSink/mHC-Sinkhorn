——写在 triton-ascend-kernels 社区算子合入之后 各位吧友好，好久不见。最近我在华为昇腾的开源仓库 triton-ascend-kernels（托管在 GitCode 上）里，从零到一开发了一个分段归约算子 reduce_segments，MR 已经合入 experimental 分支。整个过程踩了不少坑，也拿到一些还不错的性能数据。今天这篇帖子主要不是炫耀成绩，而是想把这一路的经验，尤其是那些容易让人抓狂的坑，老老实实分享给同样在搞 Triton 上昇腾 NPU、或者正打算给社区提算子的兄弟，希望能帮大家少走点弯路。 一、这个算子到底是干嘛的 reduce_segments 是一个“分段归约”算子。说得通俗点，就是把一段连续的数据，按照 segment_id 分成若干段，然后对每一段单独做 sum、max、min 这类归约运算，最后输出每一段的聚合结果。 它最常见的应用场景有这么几类： 一是 MoE 专家模型，对不同专家分片的数据做分段聚合；二是变长序列、Grouped Attention 这类场景，不同长度的样本需要分段求和、求最大值；三是图神经网络，节点按邻居关系分段聚合。 它最大的价值在于：把 segment_max、segment_sum 这类原本需要多步算子拼接的逻辑，融合进单个 Triton kernel，减少了多次 kernel launch 和反复的显存读写，端到端性能提升非常明显。 二、开发流程：从设计文档到合入 这个项目走的是“先文档、后代码”的社区评审模式，整个节奏大概是这样的： 第一步，先提 MR，上传算子设计文档。 把算子的输入输出、支持的数据类型、分段规则、归约模式、边界 case、性能考量和测试设计都写清楚，请社区评审方案合不合理。 第二步，评审通过后再写 Triton kernel 原型。 把核心逻辑用 Triton-DSL 落地，先跑通再说。 第三步，密集的缺陷修复迭代。 原型跑通后，会暴露出一堆 Triton-on-Ascend 的语法、循环变量、类型兼容问题，逐条修。 第四步，代码重构、目录规整。 清理无用参数、优化二分查找、补 README，把代码迁到任务目录结构下。 第五步，补单元测试和 benchmark。 完善自验证，把精度和性能数据都跑出来。 第六步，合入 experimental 分支。 多轮迭代后 MR 合入，交给社区开发者试用。 这里最想强调的是“设计先行”的好处：接口、边界 case、测试方案先在文档层面对齐，能避免写完一整份代码再推倒重来的尴尬。 三、踩过的坑（重点，建议收藏） 下面这些坑，每一个都让我浪费过不少时间，也是这次最想分享的干货。 1. Triton JIT 内核里不能用 Python 的 break。 Triton 的 jit 内核不支持 Python 原生 break 语句，一用就编译报错。正确做法是用 tl.where() 做谓词选择，把 break 分支改成条件选择，适配昇腾 Triton 编译器的约束。 2. 循环携带变量（loop-carried variable）的类型必须严格一致。 循环入口和出口的变量 dtype 一旦发生变化，编译能过，但计算结果会莫名其妙错掉。这点最坑，因为表面看逻辑没错，结果却是错的。必须保证循环流变量进出循环的 dtype 完全一致。 3. 二分查找里要用 Triton 的标量，别混用 Python int。 内核内部用二分查找定位元素所在分段，查找用的标量必须统一用 tl.int32，混用 Python int 会导致索引越界或类型隐式转换问题。 4. benchmark 的校验顺序要摆对。 一定要先运行 Triton kernel，再做精度校验。顺序反了，校验会在 kernel 还没执行时就比对，导致误报精度失败。 5. 目录重构后测试 import 会挂。 代码迁移目录结构后，pytest 的导入路径对不上，用例直接加载失败。补一个 conftest.py、修好 import 路径就解决了。 四、自验证结果 先说单元测试：共 7 个用例，全部通过，耗时约 58.75s，覆盖了基本单序列、多序列、小 head_size、fp32、bf16、大尺寸、多 seq 等多种情况。运行结果如图4所示。 再看性能 benchmark。项目设定的目标性能是 11.664us，自验证的 3 个场景都达标甚至大幅超标，明细如下表所示。 表1　reduce_segments 算子自验证性能结果（目标 11.664us） 场景 dtype 精度 Torch(us) Triton(us) 加速比 多序列变长 fp16 通过 646.57 4.062 159.17x 单序列长文本 fp16 通过 166.99 2.248 74.28x bf16 精度 bf16 通过 627.64 4.164 150.72x       三个场景的加速比分别达到 159.17x、74.28x、150.72x，其中单序列长文本场景性能最优（2.248us）。尤其值得说的是，多序列变长和 bf16 场景都明显优于目标 11.664us，说明算子本身的性能余量是很足的。各场景的运行日志截图如下。  图1　多序列变长场景 benchmark 结果（SpeedUp 159.17x，Triton 4.062us）  图2　单序列长文本场景 benchmark 结果（SpeedUp 74.28x，Triton 2.248us）  图3　bf16 精度场景 benchmark 结果（SpeedUp 150.72x，Triton 4.164us）  图4　reduce_segments 单元测试 7 项全部通过 五、给想入坑社区的兄弟的建议 最后，结合这次经历，给想给昇腾社区提算子的朋友几条实在的建议： 1. 先写设计文档再写代码。社区评审模式里，方案先对齐远比代码写得多重要，能省下大量返工。 2. 别把 GPU 上的 Triton 代码直接搬上来。Triton on Ascend 对 Python 控制流（break、循环内 return）和变量类型的要求更严格，很多坑都是这么来的。 3. 小步提交、拆分 commit。原型、修 bug、重构目录、补文档分开提交，reviewer 好评审，后面回溯问题也方便；合入前再按社区要求 squash 压缩。 4. 边界 case 一定要做足。空 segment、单元素、长短混合 segment，都是分段归约算子最容易出错的地方。 5. 单测和 benchmark 同步建。不只做精度对标，还要写 benchmark 验证性能收益，这两块都是社区合入的硬指标。 写在最后 这次从设计到合入，前后迭代了很多轮，中间也一度被各种莫名其妙的编译错误和错误结果搞得怀疑人生，但最后看到自己写的算子性能是 Torch 的一百多倍、还能被合进社区的时候，还是很有成就感的。 相关链接也放这儿，感兴趣的朋友可以直接去看源码和设计文档： 个人 fork 代码仓：https://gitcode.com/JaneConan/triton-ascend-kernels/tree/reduce_segments 算子设计文档（社区评审通过）：https://gitcode.com/Ascend/triton-ascend-kernels/merge_requests/107 帖子就写到这，有问题欢迎在评论区交流，也期待看到更多兄弟的算子合进社区。

在昇腾AI处理器的算子执行模型中，一个完整的计算任务遵循“GM → UB → 计算单元 → UB → GM”的数据流路径。对于由多个算子串联组成的计算图，传统实现方式为：算子A完成计算后将结果写回GM，算子B再从GM读取该结果作为输入。每一次跨算子传递都伴随着一次完整的CopyOut与CopyIn过程。 这一模式的核心问题在于：GM带宽是稀缺资源。在大模型推理场景中，KV Cache的反复搬运、中间激活张量的频繁落盘，使得GM带宽成为制约吞吐量的主要瓶颈。算子融合的核心思想是：将多个算子的计算逻辑合并到同一个Kernel中，使中间结果仅在片内UB中传递，无需经过GM。这一策略将数据流从“GM → UB → 计算 → UB → GM → UB → 计算 → UB → GM”压缩为“GM → UB → 计算1 → UB → 计算2 → UB → GM”，消除了中间环节的GM访问。 2 算子融合的硬件基础 2.1 昇腾AI Core的存储层次 理解算子融合的前提，是理解昇腾AI Core的存储架构。昇腾AI Core内部采用多级存储层次： ●GM（Global Memory） ：片外全局内存，容量大（可达数十GB），但带宽相对有限，是数据搬运的主要瓶颈。 ●UB（Unified Buffer） ：片内高速缓冲，容量较小（通常为数百KB），但访问速度远快于GM。计算前数据必须从GM搬运至UB。 ●L1 / L0A/L0B ：Cube计算路径专用缓存，用于矩阵乘等密集型计算的数据暂存。 在此架构下，数据搬运由MTE2/MTE3存储移动指令队列完成，而计算由Vector指令队列（V）或Matrix指令队列（M）完成。不同指令队列之间相互独立且可并行执行——这正是流水线优化的硬件基础。 2.2 融合如何减少GM访问 传统串行执行中，每个算子独立完成CopyIn → Compute → CopyOut三阶段，相邻算子之间通过GM传递数据。融合后，前一个算子的计算结果直接驻留在UB中，后一个算子直接从UB读取——省去了一次CopyOut和一次CopyIn。 以包含两个逐元素算子（如Add + Mul）的融合为例：融合前需要4次GM访问（输入1读、输入2读、中间结果写、最终结果读）；融合后仅需3次GM访问（两个输入读、最终结果写），GM访问量减少25%。对于更长的算子链条或更大的中间张量，收益更为显著。 3 Ascend C中的算子融合实现 3.1 融合的编程范式 在Ascend C中实现算子融合，本质上是将多个算子的计算逻辑串联在同一个Kernel的Process函数中。标准的融合实现遵循以下结构： 1.CopyIn阶段：从GM搬运输入数据到UB。 2.Compute阶段1：在UB上执行第一个算子的计算。 3.Compute阶段2：在UB上直接使用阶段1的结果执行第二个算子的计算（无需额外的CopyIn/CopyOut）。 4.CopyOut阶段：将最终结果从UB写回GM。 关键点在于：中间结果始终保持在UB中，通过LocalTensor在同一片内存储空间上传递。Ascend C的Queue（TQue）和Pipe（TPipe）机制为这一模式提供了内存管理与同步支持。 3.2 双缓冲与流水线并行 融合算子的性能不仅来源于减少GM访问，还受益于流水线并行的叠加。Ascend C支持通过double buffer机制实现CopyIn与Compute的重叠。 在融合算子中，双缓冲的收益更加明显：当Vector单元正在对当前Tile执行Compute阶段2时，MTE可以同时为下一个Tile执行CopyIn，使数据搬运时间被有效隐藏。开发者通过pipe.InitBuffer(inQueueX, 2, bufferSize)即可启用双缓冲。 3.3 融合的适用条件 并非所有算子组合都适合融合。融合的适用性取决于以下条件： ●数据依赖关系：后一个算子必须能够直接消费前一个算子的UB输出，无需跨Tile的重排或归约。 ●UB容量约束：融合后，中间结果与两个算子的输入需同时驻留UB。若UB容量不足，则需缩小Tile大小或放弃融合。 ●计算密度匹配：若两个算子均为轻量级逐元素操作，融合收益显著；若包含Reduce等复杂操作，需评估融合带来的调度复杂度。 4 实战案例 4.1 Polar算子融合：1.78倍性能提升 昇腾CANN社区任务中的Polar算子融合案例展示了融合的典型收益。Polar算子涉及复数极坐标与直角坐标的转换，包含多个数学函数调用。原始实现中，各子步骤通过GM传递中间结果，存在大量冗余搬运。 开发者将整个Polar计算流程“全程矢量化”并融合为单一Kernel。在16M数据量（[4096,4096]）的核心验收场景下，基线耗时为1665µs，融合版降至937.98µs，性能提升1.78倍。融合本身是最大的性能来源——通过消除中间结果的GM落盘，将数据流全程压缩在片内路径上。 4.2 GDN Gating融合：1.27倍至9.73倍加速 vLLM-ascend项目中的GDN Gating算子融合是另一个典型案例。GDN（Gated Delta Network）是Qwen3-Next风格模型中的核心计算模块，包含sigmoid/softplus门控与循环门控增量规则状态更新。 原始实现中，该模块由多个独立算子串行执行，中间张量在GM中反复落盘。开发者将其融合为单个Ascend C自定义算子，替代了原有的Triton Kernel实现。融合后的实现“最小化了HBM往返与中间张量物化”，在不同测试配置下取得了1.27倍至9.73倍的加速比，且零回归。 4.3 融合的工程要点 从上述案例中可以提炼出融合实现的工程要点： ●尾块处理：当数据总量无法被Tile大小整除时，需单独处理尾块（tail block）。尾块处理不当可能导致越界访问或精度异常。 ●UB内存复用：融合算子中UB空间需同时容纳多个阶段的中间结果。若复用同一块UB区域，需严格管理各阶段的读写时序，避免数据污染。 ●Tiling策略适配：融合后每个Tile内包含多个计算阶段，Tiling参数（Tile大小）需重新设计以平衡UB占用与流水线深度。 5 性能分析与优化建议 5.1 性能收益的来源 算子融合的性能收益主要来自三个方面： 1.减少GM访问次数：消除中间结果的CopyOut与CopyIn，直接降低GM带宽压力。 2.提高UB利用率：中间结果驻留UB，避免了反复的UB分配与释放开销。 3.增强流水并行度：融合后的更长计算链条为CopyIn与Compute的重叠提供了更多机会。 5.2 融合优化的边界 融合并非总是最优解。在以下场景中，融合可能收益有限甚至适得其反： ●计算量远大于搬运量：若单个算子的计算时间已远大于搬运时间，消除搬运带来的收益微乎其微。 ●UB容量紧张：融合导致单Tile数据量减小，可能降低MTE的搬运效率。 ●算子间存在复杂依赖：若后一个算子需要前一个算子的全部输出才能开始计算（而非逐Tile流水），融合无法带来流水并行收益。 5.3 调试建议 融合算子的调试复杂度高于单算子。建议采用以下策略： ●分步验证：先实现并验证各子算子的正确性，再逐步融合。 ●Profiling定位：使用msprof工具分析MTE2与Vector指令队列的流水情况，识别搬运与计算是否真正重叠。 ●精度对比：融合后与融合前的逐元素精度对比，确保数值误差在可接受范围内。

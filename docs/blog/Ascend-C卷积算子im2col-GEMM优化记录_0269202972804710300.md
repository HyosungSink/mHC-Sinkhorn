# 第一次用 Ascend C 实现卷积算子，im2col 和 GEMM 的优化之路记录；

- topicId: 0269202972804710300
- source: https://www.hiascend.com/developer/blog/details/0269202972804710300
- section: Ascend C
- createTime: 20260105052005

这个月组里分配了个任务，要在昇腾平台上实现一个定制的 2D 卷积算子，因为模型里用的 padding 和 dilation 参数比较特殊，CANN 自带的卷积算子性能不理想，只能自己写。我之前写过几个简单算子但卷积这种复杂的还是第一次，前前后后搞了快三周，把主要的坑记录一下。

技术选型上纠结了一阵，卷积实现方式主要有直接卷积、im2col+GEMM、Winograd 几种，Winograd 对 kernel size 有限制我们用不了，直接卷积实现简单但性能一般，最后选了 im2col+GEMM 的方案，虽然复杂但优化空间大；im2col 就是把输入 feature map 展开成矩阵，然后卷积变成矩阵乘法，GEMM 可以充分利用硬件的计算单元；

环境配置这次倒是没遇到太大问题，CANN 7.0 的开发环境之前搭好了，MindStudio 也能正常连接；创建 Ascend C 工程时选了个卷积的 template 作为起点，但发现模板代码只支持最简单的情况，stride、padding、dilation 都是固定的，基本要重写；编译脚本倒是能复用，省了不少配置的时间；

im2col 实现是第一个难点，要把 [N, C, H, W] 的输入展开成 [N*H_out*W_out, C*K_h*K_w] 的矩阵，考虑 padding、stride、dilation 各种参数；一开始我想直接在 Ascend C 里写这个转换逻辑，结果发现涉及大量非连续内存访问，cache miss 特别严重性能很差；参考了一些优化技巧，把 im2col 和后续 GEMM 融合到一个 kernel 里，在搬数据的时候顺便做转换，减少了中间结果的存储；

数据搬运的实现细节特别多，从 GM 搬一个 tile 的输入到 UB，这个 tile 对应输出的多个位置，要考虑 padding 区域、边界处理、stride 跳跃；写了个复杂的地址计算函数，根据输出坐标反推输入坐标，再判断是取真实数据还是填 padding 值；这个函数 debug 了好几天，各种 off-by-one 错误，画了一堆图在纸上推才理清楚；

GEMM 部分理论上是最成熟的，但映射到 Ascend C 上还是要自己实现；昇腾的 Cube 计算单元专门做矩阵乘法，但 API 不像 CUDA 的 Tensor Core 那么友好，数据排布、指令调用都有很多限制；输入矩阵要按特定 format 排列，C0 维度必须是 16 的倍数，不满足要 padding；我一开始没注意这个，传给 Cube 的数据格式不对，计算结果完全错乱；

Block 切分策略又是一个优化点，输入矩阵太大肯定一次算不完，要切成多个 block 分配给不同的 AICore；怎么切、每个 core 算多少，直接影响负载均衡和性能；试了几种切法：按输出 channel 切、按 batch 切、混合切分，每种方案的性能表现不一样；最后选了按输出 H 和 W 维度切分，能比较均匀地分配任务；

UB 内存管理这次更复杂了，im2col 的中间结果、weight 数据、输出数据、还有 GEMM 计算需要的临时 buffer，全都要塞进 UB 里；算了好几遍每个 buffer 的大小，稍微算大一点就 UB overflow，算小了又影响 tiling 效率；最后采用了分阶段复用的策略，im2col 阶段和 GEMM 阶段复用同一块 buffer，靠生命周期管理避免冲突；

双缓冲 pipeline 这次必须得上了，不然性能根本上不去；定义了两组 buffer，一组在计算的时候另一组在搬数据，用 event 同步保证数据依赖；第一次写 pipeline 逻辑时把 event 的 wait 和 record 位置搞混了，导致数据竞争，算出来结果不对；仔细看了 CANN 文档里关于 event 的说明，画了个时序图才搞明白正确的同步方式；

精度问题又来了，这次更隐蔽；功能跑通之后对比 PyTorch 的输出，大部分 case 精度没问题，但某些特定参数下误差特别大；排查了好久才发现是 im2col 时 padding 值的问题，我填的是 0 但 PyTorch 某些模式下 padding 是用 edge value，改成可配置的 padding mode 才对齐；还有个坑是 bias 的处理，GEMM 之后要加 bias，我一开始直接逐元素加，没考虑 broadcast 的情况，shape 对不上就挂了；

性能优化做了好几轮，第一版能跑但比 CANN 自带算子还慢，显然不行；用 profiling 工具分析瓶颈，发现主要问题在三个地方：一是 im2col 的地址计算太复杂，分支太多；二是 Cube 指令没充分利用，很多时间在等数据；三是不同 block 之间负载不均衡，有的算完了有的还在算；

针对这些问题逐个优化：im2col 的地址计算改成查表方式，预先算好所有坐标映射关系，虽然增加了内存占用但减少了计算开销；Cube 指令这块增加了预取和流水，让计算和数据准备重叠；负载均衡通过动态调整 block 划分策略改善，让每个 block 处理的计算量尽量一致；这几项优化下来性能提升了接近一倍；

还试了一些更激进的优化，比如循环展开、指令重排、寄存器复用，每次改一点跑 benchmark 看效果；有些优化有用有些反而变慢，性能调优真是个经验活；看了几个 CANN 官方高性能算子的实现，学到不少技巧，比如用 local tensor 做小矩阵的临时计算、合理安排 vector 指令和 scalar 指令的比例等等；

算子注册和测试这块流程和之前一样，写 info json、编译 so、配置环境变量，这次倒是轻车熟路了；测试用例设计了几十个，覆盖各种参数组合：不同的 kernel size、stride、padding、dilation、input shape，还有一些极端 case 比如 1x1 卷积、kernel 比 feature map 还大的情况；每个 case 都对比 PyTorch 的输出，数值误差控制在 1e-4 以内；

性能测试这块用的是 910B 卡，和 CANN 自带的 Conv2D 算子对比，我们特定参数下的卷积快了 35% 左右，算是达到了优化目标；但通用性肯定不如官方算子，人家支持各种 data format、quant mode 我们都没做；和 CUDA 的 cuDNN 比那差距更大，人家卷积算子优化了十几年各种 trick 都用上了，我们这点优化还差得远；

代码可维护性这次也注意了，把 im2col、GEMM、bias add 分成几个独立的函数，每个函数职责清晰；关键的地址计算、参数检查都加了注释；还写了个详细的设计文档，记录 tiling 策略、内存布局、优化思路，方便后人接手；这次吃了之前的亏，之前写的算子代码太乱自己过两周都看不懂；

总结下来几点体会：一是卷积算子复杂度比想象中高，im2col 和 GEMM 每个部分都有很多细节；二是 Ascend C 的 Cube 单元很强大但用起来门槛高，文档不够详细要多试；三是性能优化是迭代过程，不要指望一次到位，profiling 找瓶颈针对性优化；四是内存管理是永远的难点，UB 空间紧张要精打细算；五是测试覆盖要全面，卷积参数组合太多容易遗漏 corner case。下一步打算研究下 depthwise 和 group conv 的实现，看能不能复用这次的框架，有进展再分享。

# 一次 Ascend C 算子性能排查：代码没错，为什么就是跑不快？

- topicId: 02201222330040923344
- source: https://www.hiascend.com/developer/blog/details/02201222330040923344
- section: Ascend C
- createTime: 20260817062041

最近在写 Ascend C 算子时遇到一个挺典型的问题：算子功能已经跑通，结果也正确，但性能就是没有达到预期。 一开始我的思路很直接——既然计算部分最核心，那就继续优化 Compute。于是尝试减少重复计算、调整部分接口调用，甚至重新检查了一遍计算逻辑。 结果性能变化并不明显。 后来重新梳理整个 Kernel 的执行过程，才发现问题其实并不在“怎么算”，而在“数据什么时候到”。 从 Compute 跳出来看整个 Kernel 最开始我关注的代码基本集中在这里：Compute(...); 但一个完整算子的实际执行路径更接近：GM → CopyIn → LocalTensor → Compute → CopyOut → GM 这时候问题就来了： 如果 Compute 本身只需要很短时间，而 CopyIn 和 CopyOut 却占据大量时间，那么无论把计算部分优化得多漂亮，最后的收益都会非常有限。 所以我换了一个思路： 先不改代码，先判断时间到底花在哪里。 这一步看起来很简单，但其实很重要。 很多性能优化做不出效果，并不是优化手段有问题，而是一开始找错了瓶颈。 第一个检查点：是不是“搬得比算得久” 假设某个算子的核心操作只是逐元素加法：Add(dst, src0, src1, count); 这种操作本身计算强度并不高。 如果每处理一批数据，都需要：搬入 x 搬入 y 执行 Add 搬出 z 那么整个过程明显具有比较强的访存特征。 这时候继续想办法减少一两个计算指令，通常不会产生特别明显的效果。 反而应该关注：CopyIn 和 Compute 能不能重叠？ 以及：单次搬运的数据量是否合理？ 这一点让我对“算子优化”有了一个新的认识： 算子性能优化并不等于计算代码优化。 真正需要优化的是整个数据执行路径。 第二个检查点：流水有没有真正跑起来 代码里使用了 Queue、Buffer，并不意味着执行过程就一定形成了高效流水。 理想情况下，我们希望看到：        Tile 0       Tile 1       Tile 2  MTE2    CopyIn       CopyIn       CopyIn Vector       Compute      Compute      Compute MTE3              CopyOut      CopyOut      CopyOut 也就是处理当前 Tile 的同时，下一块数据已经开始准备。 但如果 Tile 数量很少，或者 Buffer 设置不合理，实际效果可能更接近：CopyIn    ↓ 等待    ↓ Compute    ↓ 等待    ↓ CopyOut 这种情况下，形式上虽然写出了 CopyIn / Compute / CopyOut，实际上硬件资源之间仍然存在大量空档。 于是我开始重新检查循环粒度。 比如原来的逻辑：for (int i = 0; i < loopCount; i++) {     CopyIn(i);     Compute(i);     CopyOut(i); } 代码本身没有问题。 真正关键的是：loopCount 到底是多少？ 如果整个数据只被拆成两三个 Tile，那么流水刚启动，任务可能就已经结束了。 这也是一个之前很容易忽略的问题： 流水除了“有没有”，还要看“够不够长”。 第三个检查点：不要默认更多核一定更快 另一个容易踩坑的思路是：性能不好 → 增加 BlockDim 乍一看很合理。 毕竟更多核意味着更多并行度。 但真正测试之后会发现，这条规律并不是一直成立。 比如一个数据规模并不大的算子，如果切到很多核：Core 0：少量数据 Core 1：少量数据 Core 2：少量数据 Core 3：少量数据 ... 每个核实际干的活越来越少。 这时候增加核数带来的收益，很可能抵不过额外的任务划分和调度成本。 所以现在我更习惯先看：总数据量 / 核数 得到每个核真正承担的数据量。 如果一个核最终只处理很小的一块数据，那么所谓“高并行”实际上可能只是把一个小任务切得过碎。 这和 CPU 多线程中的情况很像： 线程不是越多越好，核也不是越多越好。 并行度必须和任务规模匹配。 第四个检查点：Tail 数据可能比想象中麻烦 正常 Tile 往往很好处理：TileLength = 1024 TileLength = 1024 TileLength = 1024 但真实输入经常会剩下一段：TileLength = 317 这时候就会出现 Tail。 如果代码为了兼容尾块，引入大量分支：if (isLastTile) {     // 特殊逻辑 } else {     // 正常逻辑 } 虽然功能上没有问题，但对于一些规模较小的算子，这部分额外处理的占比可能并不低。 所以后来在设计 Tiling 时，我开始刻意考虑一个问题： 能不能让绝大多数数据走完全相同的快速路径，只把少量尾数据单独处理？ 这样 Kernel 主体会更加规整，也更容易继续优化。 我现在排查 Ascend C 性能问题的顺序 经历过几次类似问题之后，我现在反而不太喜欢一上来改代码。 通常先做这样一遍判断：结果正确吗？      │      └── 否 → 先解决正确性       ↓  计算型还是访存型？      ↓  核有没有吃满？      ↓  每个核的数据量是否合理？      ↓  Tile 是不是太大 / 太小？      ↓  流水有没有真正形成？      ↓  CopyIn / Compute / CopyOut 谁在等待？      ↓  最后再优化具体计算指令 相比一开始直接扎进 Compute，这种方法效率高很多。 因为最怕的并不是某个优化做失败，而是： 花了很长时间优化一个根本不是瓶颈的地方。 一个挺有意思的体会 写普通业务代码的时候，我们通常会比较关注：代码逻辑是否正确？ 但做高性能算子时，正确只是第一步。 后面还要继续问：数据在哪里？ 什么时候搬？ 一次搬多少？ 谁在等谁？ 哪些硬件资源现在是空闲的？ 从这个角度来看，Ascend C 算子优化更像是在安排一条生产线。 计算单元只是生产线中的一个环节。 真正高效的状态不是某一个工人动作特别快，而是：原料持续进入 计算持续进行 结果持续输出 中间尽可能没有停顿。 写在最后 这次排查让我印象比较深的一点是： 性能问题首先是分析问题，其次才是代码问题。 看到算子慢的时候，直接去改 Compute 往往是最自然的反应，但并不一定是最有效的。 对于 Ascend C 来说，很多时候真正值得先看的反而是数据搬运、Tiling、多核负载以及流水状态。 代码跑通以后，如果下一步不知道从哪里开始优化，不妨先问一句： “现在到底是谁在等谁？” 这个问题往往比“还能少写几条指令吗”更有价值。

0. 这道题在算什么 Scale 来自 Caffe，语义是带广播的仿射变换：output = input * scale + bias 麻烦的地方全在广播上。scale / bias 的秩通常远小于 input，通过属性 axis 指定它们对齐到 input 的哪一段维度。也就是说，同一个算子要同时应对： ●input [32, 1024]、scale [1024]—— 每行乘同一个向量； ●input [8, 64, 56, 56]、scale [64]、axis=1—— 每个通道乘一个标量， 而这个标量要覆盖56*56 = 3136个连续元素； ●以及中间的各种形态。 这两种极端的最优数据流是完全不同的：前者是向量 × 向量，后者是向量 × 标量。 一份 kernel 想同时打赢两边，就必须在运行时分流。 1. Host 侧：把任意维广播压成 [M, N, K] 整个实现的第一块基石，是 host 上的一次降维。不管输入是几维、axis 指到哪里， 一律折叠成三个数：uint32_t m = 1, n = 1, k = 1; uint32_t total_size = 1;  // M = axis 之前所有维度的乘积 for (int i = 0; i < dims; i++) {   int dim_val = input_shape->GetStorageShape().GetDim(i);   total_size *= dim_val;   if (i < axis) m *= dim_val; }  // N = scale 张量自身的总大小（严格对齐 CPU 参考实现的语义） for (int i = 0; i < scale_dims; i++)     n *= scale_shape->GetStorageShape().GetDim(i);  // K = 剩下的内部广播维度 k = (m * n != 0) ? total_size / (m * n) : 1; 含义很清楚：输入被看作 [M][N][K]，scale[j] 作用在 [i][j][0..K) 这一整段上。 ●axis支持负数（if (axis < 0) axis += dims;），沿用 Python 习惯； ●N不是从input推的，而是直接取scale的元素总数 —— 这是为了和参考实现 的num_axes/scale_from_blob语义保持一致，不自作聪明； ●K用除法反解，天然覆盖了「scale只对齐中间几维」的情况。 这一步的价值在于：后面 kernel 里所有的分支判断，都只需要看 K 和 N 两个整数， 不再需要碰原始 shape。 复杂度被彻底挡在了 host 侧。 Tiling 结构因此小得可怜，四个 uint32_t 就够了：BEGIN_TILING_DATA_DEF(ScaleTilingData)   TILING_DATA_FIELD_DEF(uint32_t, m);   TILING_DATA_FIELD_DEF(uint32_t, n);   TILING_DATA_FIELD_DEF(uint32_t, k);   TILING_DATA_FIELD_DEF(uint32_t, total_size); END_TILING_DATA_DEF; dtype 走 TilingKey 分流（1=fp32 / 2=fp16 / 3=bf16），不占 tiling 字段。 2. 核数：按数据量给，并且向上取偶uint32_t core_num = ascendc_platform.GetCoreNumAiv(); uint32_t cores = (total_size + 255) / 256;   // 每核至少 256 个元素 if (cores > core_num) cores = core_num; if (cores % 2) cores += 1;                   // 向上取偶 context->SetBlockDim(cores); 两点： 1.小 shape 主动降核。每核不足 256 个元素就不再加核 —— 对小算例，40 核的 派发开销会直接盖过计算本身。这个下限是经验值，但方向是对的：核数不是越多越好。 2.向上取偶。代码里没有注释。A2 上 AIV 是成对调度的（一个 AIC 配两个 AIV）， 我的理解是奇数块会让最后一对只用上一半，取偶让派发更规整。这一条属于现象描述， 不是我能从代码里证明的机制。 3. Kernel：四种模式，按几何选数据流 分流逻辑只有十行，但它是整个算子性能的分水岭：this->tile_elements = UB_BLOCK_BYTES / sizeof(T);   // 32 KB / 元素宽度  if (k == 1) {     if (n <= tile_elements)        this->mode = 2;   // scale/bias 全驻 UB     else if (n >= 40 * 4096)       this->mode = 3;   // 沿 N 切核     else                           this->mode = 4;   // 沿 M 切核，N 内部分块 } else {     this->mode = 5;                                  // 标量广播 } k == 1 意味着 scale 与 input 的最后一维逐元素对齐 —— 这是向量 × 向量。 k > 1 则是一个 scale 值覆盖 K 个连续元素 —— 这是向量 × 标量。 两者用完全不同的指令。 mode 2：scale/bias 常驻 UB，只加载一次 n ≤ tile_elements（fp32 下即 8192）时，广播操作数一次性读进 UB，然后核内循环 M 行， 每行只读 input、只写 output，scale/bias 零重复加载：LocalTensor sLocal = inQueueS.AllocTensor(); LocalTensor bLocal = inQueueB.AllocTensor(); uint32_t align_n = AlignTo(n, 32); DataCopy(sLocal, scaleGm, align_n); DataCopy(bLocal, biasGm, align_n); // ... EnQue / DeQue 一次 ...  for (; i != cur_end; i += iter) {     xLocal = inQueueX.AllocTensor();     yLocal = outQueueY.AllocTensor();     DataCopy(xLocal, inputGm[i * n], align_n);     inQueueX.EnQue(xLocal); xLocal = inQueueX.DeQue();      Mul(yLocal, xLocal, sLocal, align_n);     inQueueX.FreeTensor(xLocal);          // 尽早归还，让下一次 DataCopy 能启动     Add(yLocal, yLocal, bLocal, align_n);     ... } 这是最理想的情况：搬运量 = input + output，广播操作数的开销被 M 摊薄到近乎为零。 注意 inQueueX.FreeTensor(xLocal) 被放在 Mul 之后、Add 之前 —— Add 已经不需要 x 了，提前归还 buffer 能让 inQueueX 的双缓冲更早启动下一次搬运。这种「用完就还」 的细节在 Mul/Add 这种一两条指令的算子里，占比并不小。 mode 3 与 mode 4：N 太大放不下时，切谁？ n > tile_elements 时 scale/bias 装不进 UB，必须分块。此时有两种切法：  mode 3（n ≥ 163840） mode 4（其余） 核间切分 沿 N 切，每核拿一段列 沿 M 切，每核拿若干行 核内循环 外层 N 分块，内层遍历全部 M 外层 N 分块，内层遍历本核的 M scale 加载次数 每核 ceil(自己那段 N / tile) 次 每核 ceil(N / tile) 次 差别在于：N 极大时，让每个核只负责一段 N，广播操作数的加载量就按核数摊薄了。 反过来，N 不够大时按 N 切会导致核数上不去或每核活太少，于是回到按 M 切。 40 * 4096 这个阈值写得很直白 —— 40 是核数，4096 是一个经验块长， 含义是「N 大到每个核都能分到 4096 以上的列」才值得按 N 切。 mode 3 的核间切分还做了一件事：按 cache line 对齐核边界。int cache_line = 128; int lines = (n + cache_line - 1) / cache_line; int start = (lines * blockidx) / blocknum; start *= cache_line; 先把 N 按 128 个元素分组，再把组分给核。这样两个核不会读写同一条 cache line 的两半 —— 避免了跨核的伪共享与重复行取。mode 5 用的是 cache_line = 256，同样的道理。 mode 5：标量广播，以及一段值得细看的优化 k > 1 时，一个 scale 值要覆盖 K 个连续元素。此时不该用 Mul（向量×向量）， 而应该用 Muls（向量×标量）：省掉 scale/bias 的全部搬运，直接从 GM 标量读一个值。 难点在于一个 UB tile 会横跨多个 k 块，需要在 tile 内把边界切出来。 朴素写法（源码里保留为注释）是每个块都算一次除法和取模：uint32_t k_block_idx = last_elem_idx / k;   // 每块一次除法 uint32_t n_idx       = k_block_idx % n;     // 每块一次取模 优化后的版本把 div/mod 提到每个 tile 只做一次，块之间只用减法和回绕：uint32_t curr_end  = base_offset + cur; uint32_t last_blk  = (curr_end - 1;   iter = -1; cur_end = start - 1; }  for (; i != cur_end; i += iter) { ... } 效果：第 N 次跑到尾部时 L2 里是尾部数据，第 N+1 次正好从尾部开始 —— 边界处的 一段数据实现了跨 launch 命中。 几个值得说的设计细节： ●正确性不依赖计数器。正向和反向算出的结果完全相同，计数器只影响访问顺序。 所以即使 workspace 首次未清零、初值是随机的，也不会算错，最多是第一次方向不理想。 ●只有 0 号核累加（if (GetBlockIdx() == 0)），避免 40 个核同时读改写同一个地址。 6. bf16：没有原生算术，还得复刻参考实现的舍入 A2 上 bf16 没有向量算术指令，所有计算必须 Cast 到 fp32 再做。所以 bf16 单独走了 一个类 KernelScaleBf16，而不是模板特化。 真正反直觉的是这一段：Cast(xyLocal_32, xLocal, RoundMode::CAST_NONE, align_n);   // bf16 -> fp32  Mul (xyLocal_32, xyLocal_32, sLocal_32, align_n);          // 乘 Cast(yLocal,     xyLocal_32, RoundMode::CAST_RINT, align_n);   // fp32 -> bf16  ← 故意的 Cast(xyLocal_32, yLocal,     RoundMode::CAST_NONE, align_n);   // bf16 -> fp32  ← 故意的 Add (xyLocal_32, xyLocal_32, bLocal_32, align_n);          // 加 Cast(yLocal,     xyLocal_32, RoundMode::CAST_RINT, align_n);   // 最终输出 中间那两次 Cast 在数学上完全是浪费 —— 全程留在 fp32 里精度更高。 但参考实现是把乘法的中间结果存回 bf16 的，所以「更高的精度」反而会让结果对不上 golden。 这条经验值得单独记住：精度验收比的是「和参考实现一致」，不是「和数学真值一致」。 当参考实现有精度损失时，你必须把那份损失精确复刻出来，包括舍入模式 （这里是 CAST_RINT，即 round-to-nearest-even）。 7.

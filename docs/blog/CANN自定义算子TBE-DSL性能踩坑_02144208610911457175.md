# CANN 自定义算子开发的两个半月踩坑实录，从 TBE DSL 编译报错到算子性能超越框架自带版本 40%

去年四月做 OCR 文本识别模型 CRNN 的推理部署，网络里用了个 STN（Spatial Transformer Network）做几何校正。PyTorch 训练时用 torch.nn.functional.grid_sample 实现，转 ONNX 后是 GridSample 算子。用 ATC 转换模型时直接报错 "Operator GridSample is not supported"，CANN 6.3 根本没这个算子。查了官方算子列表，GridSample 确实不在支持范围。试了几个 workaround，把 GridSample 拆成一堆基础算子，性能惨不忍睹，单次推理 300ms，其中 GridSample 部分就占 180ms。没办法只能自己写算子，用 TBE（Tensor Boost Engine）开发自定义算子。以为就是写个 kernel 函数，结果 TBE 的 DSL 语法、UB 寄存器分配、schedule 调度、编译链路、调试方法每个环节都是坑。从第一版能跑到性能达标，整整磨了两个半月，把 TBE 的开发文档翻烂了。

硬件环境先说，Atlas 300I 推理卡，4 个 310P 芯片，每个 8GB 内存。系统 Ubuntu 20.04，驱动 23.0.3，CANN 7.0.0。开发环境用 MindStudio 3.0，自带 TBE 插件和调试工具。模型是 PyTorch 1.11 训练的，输入图片 1x3x64x256，STN 输出校正后的特征图。GridSample 的输入是 feature map [N,C,H,W] 和 grid [N,H,W,2]，输出是采样后的 map。

GridSample 的功能研究了下，根据 grid 坐标在 feature map 上双线性插值采样。Grid 的坐标范围是 [-1,1]，对应 feature map 的边界。padding_mode 支持 zeros、border、reflection，align_corners 控制对齐方式。算法不复杂，但要高效实现不容易。

开发环境搭建先踩坑，MindStudio 装了半天，依赖一堆 Python 包。TBE 需要特定版本的 te（Tensor Engine）和 topi 库，pip install te-0.4.0.whl。环境变量 export LD_LIBRARY_PATH、PYTHONPATH 配了一堆。创建 TBE 算子工程，目录结构是 op_proto、op_impl、framework 三个部分。

算子原型定义是第一步，写 grid_sample.py 的 op_proto。用 @OpSchema 装饰器定义算子签名，输入输出的 tensor 类型、shape、dtype。看了几个例子，照猫画虎写了个：

Python

```
@OpSchema("GridSample")
def grid_sample(input_tensor, grid, output, align_corners=True, padding_mode="zeros"):
    pass
```

编译报错，"OpSchema requires complete type annotation"。改了半天，每个参数都要 annotation。input_tensor: "required", dtype: "float16,float32"，shape 用 DSL 描述。写了 20 行代码，各种括号引号，格式错一点就编译不过。

算子实现是核心，op_impl/grid_sample_impl.py。用 TBE 的 DSL 写计算逻辑，这个 DSL 很诡异，不是直接写 kernel，而是描述 schedule。用 te.compute 定义计算图，lambda 表达式写逻辑。

第一版照着文档写了个最简单的：

Python

```
def grid_sample_compute(input_tensor, grid):
    shape = input_tensor.shape
    def _compute(n, c, h, w):
        gx = grid[n, h, w, 0]
        gy = grid[n, h, w, 1]
        # bilinear interpolation
        ...
    output = te.compute(shape, _compute, name="output")
    return output
```

编译又报错，"Cannot use dynamic index in te.compute"。grid[n,h,w,0] 这种动态索引不支持，要改成静态 schedule。看了文档，动态索引要用 te.gather 或者 cache 到 UB（Unified Buffer）。

UB 是 310P 的片上缓存，256KB，要手动管理。把 grid 先 cache 到 UB，再读取。加了 cache_read，grid_ub = te.cache_read(grid, "local.UB", [output])。又报错，"UB overflow, available 256KB, required 512KB"。Grid 太大，cache 不下，要分块处理。

Tiling 策略研究了，把输出 shape [N,C,H,W] 切成小块，每块 tile_h x tile_w。每次处理一个 tile，UB 只需要存当前 tile 的 grid。写了个 schedule：

Python

```
s = te.create_schedule(output.op)
h_outer, h_inner = s[output].split(output.op.axis[2], factor=16)
w_outer, w_inner = s[output].split(output.op.axis[3], factor=16)
```

编译通过了，生成 .cce 文件。但 simulate 仿真时报错，"Invalid memory access"。调试 TBE 特别痛苦，没有 printf，没有 gdb，只能看寄存器 dump。

开了 TBE 的 debug 模式，设置 export TBE_DEBUG=1。生成详细的 schedule tree 和 IR。看 IR 发现 bilinear 插值的边界没处理，坐标超出 [0,H-1] 时访问越界。

边界处理加了 clip，gx = te.min(te.max(gx, 0), W-1)。但 TBE 的 min/max 不支持在 te.compute 里直接调，要用 topi.clip。改了又编译不过，clip 的输入输出类型不匹配。折腾了两天，终于用 te.if_then_else 实现了 clip。

Padding mode 的支持又是个坑，zeros、border、reflection 三种模式。Zeros 简单，越界返回 0。Border 是 clamp 到边界。Reflection 是镜像，坐标翻转。写了一堆 if-else，代码膨胀到 200 行。

编译终于通过，仿真也过了。注册算子到框架，写 framework/caffe_grid_sample_plugin.cc。实现 InferShape 和 GetOpSupportedType 函数，返回输出 shape 和支持的 dtype。编译 plugin，生成 .so 文件。

把算子集成到模型转换，ATC 的 --insert_op_conf 指定算子映射。ONNX 的 GridSample 映射到自定义的 GridSample。转换模型，居然成功了，生成 .om 文件。

推理测试跑了下，能出结果，但精度不对。和 PyTorch 的输出对比，误差高达 1e-2，远超正常范围。Dump 了中间结果，发现 bilinear 插值的系数算错了。

坐标转换有 bug，grid 的 [-1,1] 要映射到 [0,W-1]。公式是 x = (gx + 1) * (W - 1) / 2。代码里写成了 x = gx * W / 2 + W / 2，align_corners=False 时对，True 时错。改了公式，精度对齐了，误差降到 1e-6。

性能测试让人失望，单次 GridSample 要 85ms，虽然比 workaround 的 180ms 快，但 PyTorch CPU 版本只要 60ms。自定义算子居然比 CPU 慢，完全不能接受。

Profiling 分析了性能，用 msprof 看 timeline。GridSample 分成了 32 个 kernel launch，每个处理一个 tile，launch overhead 大。Tile 太小了，16x16 一个，总共 4x16=64 个 tile，但只启动了 32 个，说明某些 tile 串行了。

Schedule 优化调整 tile 大小，factor=32，每个 tile 32x32。Kernel 数量降到 8 个，launch overhead 减少。性能提升到 65ms，接近 CPU 了。

并行度还不够，看 schedule tree，发现 N 和 C 维度没并行。加了 bind 到 block 和 thread，s[output].bind(n_axis, te.thread_axis("blockIdx.x"))。但 310P 不是 CUDA，没有 thread 概念，这个 bind 不生效。

改成 TBE 的并行方式，用 AICore 的向量单元。把 C 维度向量化，一次处理 16 个 channel。用 te.vectorize 标记，s[output].vectorize(c_inner)。编译报错，"Cannot vectorize non-contiguous axis"。

内存 layout 调整，输入 tensor 的 C 维度要连续。检查发现输入是 NCHW，C 在外层，不连续。改成 NHWC layout，C 在最内层。但改 layout 影响其他算子，整个模型要一起改。

用 transpose 算子先转成 NHWC，GridSample 处理完再转回 NCHW。虽然增加两次 transpose，但向量化收益更大。性能测试 55ms，快了 15%。

UB 利用率优化，profiling 看到 UB 只用了 60KB，256KB 的容量浪费。增大 tile 大小，64x64 一个 tile，UB 用到 180KB。但 tile 太大，边界处理复杂，性能反而下降到 70ms。

Double buffer 优化用上了，一个 buffer 在计算，另一个在搬数据。TBE 的 double_buffer 接口，s[grid_ub].double_buffer()。计算和搬运 overlap，性能提升到 48ms。

指令级优化又做了一轮，bilinear 插值的 4 次乘法和 4 次加法。用 vmadd 指令融合乘加，减少指令数。TBE 的 intrinsic 接口，tvm.call_extern("vmadd", ...)。手写汇编级优化，提升 10%，42ms。

Cache 策略调了，输入 feature map 也 cache 到 UB。但 feature map 太大，64x256x512，cache 不下。只 cache 当前 tile 需要的部分，根据 grid 的范围计算。写了个 prefetch 逻辑，提前加载下一个 tile 的数据。

数据重用优化，同一个 grid 点附近的采样点会重用相同的 feature。把 feature map 按 tile 组织，提高 cache hit rate。这个优化很复杂，改了一周，性能提升到 38ms。

多核并行终于搞定了，310P 有 2 个 AICore，可以并行。把 N 维度切分，每个 core 处理一半。TBE  block 配置，s[output].split_block(factor=2)。测试后性能 22ms，几乎翻倍。

对比 CPU 的 60ms，NPU 的 22ms 快了 2.7 倍，终于有加速效果了。和 workaround 的 180ms 比，快了 8 倍。整个模型推理从 300ms 降到 140ms，提升 53%。

精度对齐又仔细测了，不同 padding mode、align_corners 的组合都试了。Zeros 模式有个 corner case，grid 刚好在边界时，插值系数计算有舍入误差。改成先判断边界，精确处理。

不同数据类型支持了，FP32、FP16 都测试。FP16 要注意下溢，某些中间计算会溢出。加了 cast 和 clip，保证数值稳定性。

算子注册到 MindSpore 和 ONNX-CANN 的映射表。写了 grid_sample.json，定义算子属性。测试了 CRNN 模型，端到端推理 142ms，正确率和 PyTorch 一致。

其他模型也试了，只要用到 GridSample 的都能复用。STN、Deformable Attention、Optical Flow 这些网络都有 GridSample。算子库开源后，好几个团队在用。

调试工具摸透了，TBE Profiler 可以看指令级性能。UB 的 bank conflict、pipeline stall、vector utilization 都能分析。学会用 TBE Debugger，设置断点，单步执行，查看寄存器。

版本兼容性测试了，CANN 6.3 和 7.0 的 TBE API 有差异。写了 version check，兼容两个版本。某些 intrinsic 在老版本不支持，要降级实现。

文档写了完整的算子开发教程，从 DSL 语法、schedule 优化、调试技巧到性能调优。代码加了详细注释，关键 schedule 解释清楚。提交到 CANN 社区，收录到官方算子库。

错误处理加了，输入 shape 不合法、dtype 不支持、参数越界都要检查。返回明确的错误码和信息，方便用户定位问题。

单元测试写了 pytest，各种 shape、dtype、参数组合。对比 PyTorch 的 grid_sample，逐像素验证。测试覆盖率 90%，保证质量。

性能 benchmark 记录了，不同 shape 的耗时。64x256 输入 22ms，128x512 输入 78ms，256x1024 输入 285ms。做成表格，给用户参考。

踩坑总结几点：第一，TBE 的 DSL 学习曲线陡，要多看例子；第二，UB 内存管理是难点，tile 策略很关键；第三，调试工具要熟练，仿真和 dump 是主要手段；第四，性能优化要 profiling 驱动，找瓶颈；第五，精度对齐很重要，边界条件要仔细测；第六，文档和测试必不可少，否则别人用不了。

后续优化还想做几个，试试 FP16 的 tensor core 加速，研究 sparse grid 的优化，支持 3D GridSample。这些在 TODO 里，慢慢迭代。

TBE 算子开发门槛确实高，但性能收益明显。对某些特殊算子，自己写比等官方支持快。CANN 的算子生态还在建设，希望越来越完善。

# Ascend C 写图像预处理融合算子的踩坑全记录，从单算子到融合优化的性能提升之路；

三月初做一个目标检测的项目，推理服务部署在昇腾310P上，模型前面有一长串图像预处理操作，Resize、ColorSpace转换、Normalize、Transpose这些步骤一个接一个。用PyTorch或者ONNX Runtime跑的时候，这些预处理步骤都是独立的算子，每个算子之间要把数据从NPU写回内存再读回来，反复搬运数据特别慢。测了下单张图片预处理要40ms，模型推理才30ms，预处理比推理还慢，完全不能接受。研究了一圈决定用Ascend C把所有预处理操作融合成一个算子，一次性在NPU上完成，减少数据搬运。从开始写到最后优化完用了快两个月，Ascend C的坑踩了个遍。

需求这块先梳理清楚，输入是1920x1080的RGB图片，JPEG解码后的数据；要做的操作按顺序是：先把RGB转成BGR格式适配模型，然后Resize到640x640，接着减均值除方差做归一化，最后HWC转成CHW排布。原来的方案是调用OpenCV的函数或者用PyTorch的transforms，每个操作都是独立的，中间结果要保存到内存。CPU上跑这些操作也慢，换到NPU上跑虽然快点，但算子调度和数据搬运的开销占了大头。看了下NPU的利用率只有30%，大部分时间在等数据。

Ascend C开发环境这次用的是CANN 7.0.1版本，比之前7.0稳定一些。MindStudio IDE装了最新版，调试功能加强了不少，能看变量值了。编译工具链ccec也更新了，编译速度快了一倍。但Ascend C的文档还是那样，很多API只有函数名没有详细说明，要靠试。社区论坛上也没几个人在用Ascend C，问题基本没人回答，只能自己摸索。

第一版实现思路很简单，把所有操作写在一个核函数里，输入RGB图片输出CHW的Tensor。数据流是从Global Memory加载原图到L1 Buffer，在L0 Buffer上做各种变换，最后写回Global Memory。听起来很直接，实际写的时候到处是坑。首先是Resize操作，双线性插值要访问周围4个像素点，坐标计算和权重计算都要精确。写了个标量版本的双线性插值，一个像素一个像素算，跑起来慢得离谱，单张图要200ms，比原来还慢。

向量化改造花了很长时间，双线性插值不像矩阵乘法那么规整，很难向量化。研究了好几天，发现可以把插值拆成两步，先水平方向插值再垂直方向插值，这样每一步都是规整的向量操作。用Ascend C的Load Repeat指令加载一行像素，Mul和Add指令做加权求和。向量化之后速度提升到50ms，但还是不够快。

内存访问模式也有问题，Resize的时候源图和目标图的访问模式不连续。源图按照插值坐标跳跃访问，缓存命中率很低。改了数据排布，源图按行分块加载到L1，保证每个块内的访问是连续的。还做了预取，提前把下一块数据加载到另一个Buffer，计算和加载并行。这样优化后Resize降到30ms，勉强能用了。

ColorSpace转换RGB到BGR相对简单，就是通道顺序调换。但要和Resize融合在一起就麻烦了，Resize输出的数据要立刻做通道交换，不能写回Global Memory再读。用了L1 Buffer做中转，Resize的输出直接写到L1，ColorSpace转换从L1读取再写回L1。这样避免了Global Memory的往返，省了不少带宽。

Normalize操作是减均值除方差，公式简单但要注意数值精度。输入是uint8的图像数据0到255，要转成float32做运算。Cast指令做类型转换，但一次只能转一个向量。写了个循环批量转换，转完再做减法和除法。除法比乘法慢，改成乘以方差的倒数，提前算好倒数存起来。还要注意除零的情况，方差不能是0，加了个很小的epsilon避免除零。

Transpose操作HWC转CHW是最难优化的部分，涉及大量的非连续访问。原来的数据排布是[H, W, C]，一个像素的三个通道挨在一起。转成[C, H, W]后，同一个通道的所有像素要挨在一起。直接转置的话要跳跃访问，缓存全miss。试了好几种方案，分块转置、寄存器转置、共享内存转置，最后发现分块加向量shuffle效果最好。

分块转置的思路是把输入分成16x16的小块，每个块内做转置。用向量指令Load一批数据，用Shuffle指令重新排列。Ascend C有个VEC_SHUFFLE指令，能按照指定模式重排向量元素。配置好Shuffle的pattern，一条指令就能完成一小块的转置。但pattern的配置很复杂，看文档看了半天也没完全理解，最后是照着例子改的。

算子融合的时候遇到内存不够的问题，L1 Buffer只有几百KB，放不下所有中间结果。原图1920x1080x3要6MB，Resize后的640x640x3要1.2MB，这些都放L1不现实。只能分块处理，一次处理一部分数据。把输入图按行分成多个Block，每个Block 64行，一次加载64行到L1做处理。但分块后Resize的边界处理很麻烦，需要访问相邻Block的数据做插值。做了个Overlap策略，每个Block多加载上下各2行的数据，保证边界插值有足够的像素。

流水线优化又是一轮迭代，分块处理后可以做流水线并行。当前Block在计算时，下一个Block提前加载数据。用了三个Buffer轮转，一个在加载，一个在计算，一个在写出。Pipe机制管理这三个Buffer的调度，Enque和Deque接口控制流水线节奏。但Pipe的深度设置有讲究，太深了占内存，太浅了流水线断档。试了几个值，深度3效果最好。

向量化程度继续优化，一开始很多地方还是标量操作，循环展开做向量化。Ascend C的向量长度是硬件相关的，FP32的向量是64个元素，FP16是128个。为了充分利用向量单元，把数据类型从FP32改成FP16。精度损失测试了下，对最终检测精度影响在0.5%以内，可以接受。FP16的向量化后性能提升明显，计算部分快了一倍。

边界条件处理也是个细节坑，图像大小不一定是向量长度的整数倍。最后几个像素要单独处理，用Mask机制控制只处理有效元素。Mask的生成也是向量化的，Compare指令生成Mask向量。有效位为1，无效位为0，向量操作只影响有效位。这样避免了标量循环，保持了向量化的连续性。

精度对齐是调试时的大麻烦，融合算子的输出要和原来的预处理结果一致。逐元素对比发现有些像素差了好几个值，误差超过容忍范围。排查发现是Resize插值的计算精度问题，浮点运算顺序不同导致累积误差。调整了计算顺序，先乘后加改成先加后乘，减少了中间结果的舍入误差。还把一些常数从FP16改成FP32计算，精度对齐后误差降到1以内。

性能测试终于看到效果了，融合算子的预处理时间从40ms降到8ms，提升了5倍。其中Resize占3ms，ColorSpace和Normalize合计2ms，Transpose占3ms。对比原来的单独调用，Resize从15ms降到3ms，Transpose从12ms降到3ms，其他操作也都有提升。最关键的是算子调度开销没了，数据搬运次数从5次降到1次，带宽节省了80%。

吞吐量测试batch size设成8，8张图一起处理。融合算子支持batch并行，8张图的时间是25ms，平均每张3.1ms。batch越大均摊的启动开销越小，但L1 Buffer装不下太大的batch。测试了不同batch size，8是性能最优的点，再大就要分多次处理了。

功耗和温度也监控了，NPU利用率提升到85%，功耗从10W涨到18W。但总的处理时间短了，能效比还是提升的。温度稳定在65度左右，散热没问题。对比CPU预处理功耗30W，NPU还是省电很多。

算子注册到PyTorch框架写了Python的wrapper，torch.classes.load_library加载so库。自定义torch.autograd.Function包装前向传播，反向传播不需要，预处理没有梯度。C++扩展写了ATen的接口，把Tensor转成Ascend的buffer，调用底层算子。类型转换和内存拷贝要注意，Tensor的data_ptr()拿到指针，但要确保内存是连续的。

实际部署的时候又遇到新问题，推理服务用的是MindX SDK，不是PyTorch框架。查了文档发现MindX也支持自定义算子，但接口不一样。重新写了一套适配MindX的wrapper，用AscendCL的接口加载算子。配置文件也要改，om模型的配置里加上自定义算子的路径。测试了几轮才跑通，MindX的错误信息更难懂。

多线程并发也测试了，推理服务是多线程的，每个线程处理一路视频流。自定义算子要支持并发，Context要线程独立。用thread_local存储每个线程的Context，避免资源竞争。测试了4线程并发，每个线程能稳定跑到8ms的性能，没有冲突和死锁。

错误处理也完善了，算子执行失败要有清晰的错误码和日志。输入参数检查放在最前面，shape不对、类型不对都要报错几回。中间计算出现异常也要捕获，比如内存分配失败、指令执行超时。返回错误码给上层，Python能catch到异常继续处理。

版本兼容性测试了CANN 6.3和7.0两个版本，发现一些API不兼容。用宏定义做版本判断，不同版本调用不同的接口。尽量用稳定的API，避免用实验性的功能。文档标注了哪些API是deprecated的，这些都不用。

实际场景跑了一周，处理了几百万张图片，稳定性没问题。偶尔有张图片预处理失败，看日志是输入数据异常，不是算子的问题。加了输入校验，对明显异常的输入直接拒绝，返回错误码。统计了失败率在万分之一以内，业务可以接受。

性能对比做了详细的表格，CPU预处理50ms，原生NPU算子40ms，融合算子8ms。端到端的推理时延从70ms降到38ms，FPS从14提升到26。达到了实时处理的要求，4路1080p视频能同时跑起来。

成本收益也算了，开发耗时两个月，代码3000多行。性能提升5倍，推理服务器数量能减少60%。服务器成本一台10万，省下来几十万。开发投入和收益比很划算，而且经验可以复用到其他项目。

后续优化还有空间，ColorSpace转换可以用查表法代替计算，提前建表。Normalize的均值方差如果是固定的，可以编译时烙进算子里，省去运行时读取。Transpose也可以试试其他算法，Tiled transpose或者recursive transpose。这些都列在TODO里，有时间再优化。

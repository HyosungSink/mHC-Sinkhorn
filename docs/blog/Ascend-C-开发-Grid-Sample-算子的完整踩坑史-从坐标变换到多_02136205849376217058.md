# Ascend C 开发 Grid Sample 算子的完整踩坑史，从坐标变换到多模式插值的优化探索之路；

十一月份做光流估计模型部署，RAFT 和 PWC-Net 这些光流网络里大量用到 Grid Sample 操作，根据光流场对图像做 warping。整个推理流程跑下来发现 Grid Sample 层慢得要命，单层要 32ms，模型里有七八层，加起来占了整体推理时间的 45%。PyTorch 的 grid_sample 在昇腾上只有 CPU 实现，数据要在 NPU 和 CPU 之间来回搬，延迟高得离谱。查了一圈发现昇腾平台没有现成的 Grid Sample 算子，torchvision 的昇腾适配也没有这个。研究后发现只能用 Ascend C 自己实现，把 Grid Sample 从零写一遍。听起来就是坐标变换加插值，实际开发时才发现坐标归一化、边界处理、多种插值模式、多种 padding 模式，每个组合都是坑。从开始到优化完用了整整两个月，把 Grid Sample 的各种细节、边界情况、性能优化全摸了个遍。

需求这块先理清楚，Grid Sample 是 STN 空间变换网络提出的，用于对特征图做任意的空间变换。输入是特征图 input [N, C, H_in, W_in] 和采样网格 grid [N, H_out, W_out, 2]。grid 的最后一维是 (x, y) 坐标，指定输出的每个位置应该从输入的哪个位置采样。坐标是归一化的，范围通常是 [-1, 1]，-1 对应最左或最上，1 对应最右或最下。输出是 [N, C, H_out, W_out]。关键参数有三个：interpolation mode 插值模式（bilinear、nearest、bicubic），padding mode 边界模式（zeros、border、reflection），align_corners 对齐方式。这个算子看着简单，实际上组合爆炸，3 种插值 × 3 种 padding × 2 种对齐 = 18 种组合，每种都要实现和测试。而且坐标是浮点数，归一化和反归一化要精确，边界处理要仔细，稍有不慎结果就错了。

开发环境用的 CANN 7.0.1，MindStudio 调试工具越用越熟练。Ascend C 的文档里没有 Grid Sample 的任何参考，只能看 PyTorch 源码和 CUDA 实现。PyTorch 的 C++ 实现看了，逻辑清晰但全是模板和条件分支，针对不同模式有不同代码路径。CUDA 版本看了 ATen 的实现，用了很多优化技巧，但线程模型和 Ascend C 不一样。

第一版实现选了最简单的配置，bilinear 插值 + zeros padding + align_corners=True。四层循环遍历输出的每个位置，外层 batch 和 channel，内层 h、w。对每个输出位置 (n, c, h, w)，读取 grid[n, h, w] 得到采样坐标 (x, y)。坐标归一化在 [-1, 1]，要反归一化到像素坐标。公式是 ix = ((x + 1) * (W_in - 1)) / 2，iy 同理，这是 align_corners=True 的情况。得到浮点坐标 (ix, iy) 后做双线性插值，找周围 4 个像素加权平均。写了个 bilinear_sample 函数，输入特征图、浮点坐标、padding 模式，输出插值结果。

第一版跑起来性能惨不忍睹，单层要 85ms，比 CPU 的 32ms 还慢一倍多。全是标量操作，每个输出像素单独处理，完全没向量化。而且采样坐标随机，访存全是 Cache Miss。Msprof 看了下 NPU 利用率只有 12%，大部分时间在等数据。

坐标归一化的计算优化了下，反归一化公式 ix = ((x + 1) * (W_in - 1)) / 2，每个像素都要算一遍。除法慢，改成乘法，预计算 scale = (W_in - 1) / 2，公式变成 ix = (x + 1) * scale。但 scale 要存起来，每个输出位置读一次。还不如直接算，因为除以 2 是位移操作。最后用的是 ix = (x + 1) * (W_in - 1) * 0.5，0.5 的乘法比除法快。

align_corners 的处理踩了个坑，True 和 False 的归一化公式不一样。align_corners=True 时，-1 对应像素 0 的中心，1 对应像素 W_in-1 的中心。align_corners=False 时，-1 对应像素 -0.5，1 对应像素 W_in-0.5，坐标往右偏移了半个像素。公式变成 ix = (x + 1) * W_in / 2 - 0.5。测试的时候结果老对不上，调了半天才发现是这个差异。

双线性插值的实现又遇到边界问题，采样坐标可能超出 [0, W_in-1] 范围。超出时根据 padding_mode 处理。zeros 模式返回 0，border 模式 clamp 到边界，reflection 模式镜像反射。写了三个版本的插值函数，根据 padding_mode 调用不同版本。但三个函数代码 90% 重复，只有边界处理不同。重构成一个函数，用 if 判断 padding_mode。但 if 在循环里，分支预测失败影响性能。

向量化改造研究了很久，Grid Sample 的难点是每个输出位置的采样坐标都不同，无法批量处理。试了在 channel 维向量化，一次处理 64 个 channel。所有 channel 从同一个坐标采样，可以一起插值。但插值要访问 4 个位置，每个位置加载 64 个 channel，4 次加载。用 Gather 指令，但 Ascend C 的 Gather 对浮点索引支持不好，要先 floor 转整数。

并行策略调整了，按输出位置并行。每个 Block 处理一个 (n, h, w) 位置，Block 内遍历 channel。多个 Block 并行处理不同位置，充分利用多核。但 Grid Sample 的特点是每个位置独立，没有数据依赖，并行度很高。测试了下性能提升到 45ms，有改善但还不够。

特征图预加载到 L1 Buffer，减少 GM 访问。一个 channel 的特征图 H_in * W_in 个 FP32，如果是 256x256 就 256KB，L1 放不下。分批加载，一次加载 16 个 channel。但不同输出位置采样的区域不同，预加载的效果有限。改成按需加载，只加载采样区域覆盖的部分。但采样区域的计算也有开销，权衡后还是全加载，依赖 Cache 自然淘汰。

Nearest 插值模式实现起来简单，不需要插值权重。采样坐标四舍五入取最大的整数像素。公式是 ix = round(ix_float)，iy = round(iy_float)。但 round 的边界情况要注意，0.5 是向上还是向下，要和 PyTorch 一致。测试发现 PyTorch 用的是 round-to-even，0.5 向最近的偶数。写了个自己的 round 函数，保证一致性。

Bicubic 插值模式最复杂，要访问周围 16 个像素。权重计算用三次多项式，公式很长。参考了 OpenCV 的实现，cubic 函数 f(x) = (a+2)|x|^3 - (a+3)|x|^2 + 1 for |x| <= 1。a 是参数，通常取 -0.5 或 -0.75。实现了 bicubic_interpolate 函数，循环 4x4 的邻域计算权重累加。但 16 个像素的访问，Cache Miss 率很高，性能很差。优化了访存顺序，按行访问，提升 Cache 命中率。

Reflection padding 的实现又是个坑，镜像反射的边界规则很复杂。坐标小于 0 时，reflect 成 -x - 1（还是 -x？）。坐标大于 W_in - 1 时，reflect 成 2 * (W_in - 1) - x。但边界反射可能多次，要用 while 循环反复 reflect 直到回到范围内。写了个 reflect_coordinate 函数，输入坐标和范围，输出 reflect 后的坐标。测试了各种边界情况，坐标是 -10、100 这种远超范围的，都要能正确 reflect。

Border padding 就是 clamp，比较简单。坐标小于 0 取 0，大于 W_in - 1 取 W_in - 1。但 clamp 后的坐标还是浮点数，插值时四个角点可能重复。比如坐标 (-0.3, 0.5)，clamp x 到 0 后，四个角点变成 (0, 0), (0, 1)，只有两个不同。插值权重要重新计算，不然结果错。

梯度计算是又一个大坑，Grid Sample 的反向传播要算两个梯度：input 的梯度和 grid 的梯度。input 梯度是把输出梯度通过插值反向传播回去，和 RoIAlign 的梯度类似。Grid 梯度要算采样位置对输出的影响，涉及插值权重对坐标的导数。Bilinear 的导数推导了下，d(interp(x, y)) / dx 要算出来。Bicubic 的导数更复杂，三次多项式求导。写了两周才把梯度算对，数值梯度检查反复调试。

Align_corners 的梯度也不一样，归一化公式不同导致梯度的 scale 不同。align_corners=True 时，梯度要乘以 (W_in - 1) / 2。align_corners=False 时，梯度乘以 W_in / 2。这个细节调了好久才发现，梯度检查一直过不了。

不同 padding 模式的梯度处理也不同，zeros 模式超出范围的梯度是 0。border 模式边界上的梯度要累加，多个采样点可能 clamp 到同一个像素。reflection 模式梯度要反向 reflect 传播。每种模式写了单独的梯度计算函数。

原子操作又用上了，反向传播时多个输出位置的梯度累加到同一个输入位置。多个 Block 并发写，要用 AtomicAdd 保证正确性。但原子操作慢，优化策略是每个 Block 先在本地累加，最后一次性原子加。

性能测试终于看到提升，优化后的 Grid Sample (bilinear + zeros) 从 85ms 降到 15ms，提升了 5 倍多。对比 CPU 的 32ms，快了一倍。Nearest 模式更快，8ms，因为不用插值。Bicubic 模式慢，28ms，16 个像素的访问开销大。

不同 padding 模式测试了，zeros 最快 15ms，border 稍慢 17ms（clamp 有开销），reflection 最慢 22ms（reflect 计算复杂）。

不同输入大小测试了，[1, 3, 256, 256] grid [1, 256, 256, 2] 是 15ms。[1, 64, 128, 128] grid [1, 128, 128, 2] 是 8ms。[1, 256, 512, 512] grid [1, 512, 512, 2] 是 58ms。输入越大越慢，但基本线性增长。

功耗和温度监控了下，Grid Sample 的 NPU 利用率 40%，主要是访存密集。功耗 10W，温度 58 度，散热没问题。

算子注册到 PyTorch 框架写了扩展，接口和 torch.nn.functional.grid_sample 一致。输入是 input, grid, mode, padding_mode, align_corners。mode 是 'bilinear'、'nearest'、'bicubic' 之一。padding_mode 是 'zeros'、'border'、'reflection' 之一。

单元测试写了上百个 case，18 种模式组合都要测。每种组合测试不同的输入大小、不同的 grid 范围。对比 PyTorch 的实现，前向误差在 1e-4 以内。反向梯度误差稍大，1e-3 左右，主要是 bicubic 的精度差异。

实际部署在 RAFT 光流模型上，整个推理流程测试了端到端性能。推理时间从 420ms 降到 280ms，Grid Sample 不再是瓶颈。光流精度没有变化，EPE 和 PyTorch 一致。

PWC-Net、LiteFlowNet 这些网络也测试了，都用到 Grid Sample。性能都有 40% 以上的提升，效果不错。

STN 空间变换网络也测试了，Grid Sample 是核心操作。变换后的图像质量和 PyTorch 完全一样，没有精度损失。

多线程并发测试了 4 个线程，每个线程处理一张图。线程安全，Context 隔离。4 线程吞吐量是单线程的 3.4 倍，扩展性还行。

错误处理加了输入检查，grid 的 shape 要和 input 匹配。grid 的最后一维必须是 2。mode 和 padding_mode 参数要合法。内存分配失败要捕获，返回错误码。

版本兼容性测试了 CANN 不同版本，7.0 和 6.3 接口一致。PyTorch 1.11、2.0 都能用。ONNX 导出有点问题，grid_sample 是 ONNX 算子，但参数映射要注意。

线上运行了三周，处理了几万对图像，稳定性很好。偶尔有几次输出异常，看日志是 grid 的值超出 [-1, 1] 很远，采样位置离谱。加了 grid 的 clamp，限制在 [-2, 2] 范围，超出的 clip 掉。

性能对比记录了数据，CPU Grid Sample 32ms，自定义 NPU (bilinear) 15ms，提升 2.1 倍。端到端 RAFT 从 420ms 降到 280ms，FPS 从 2.4 提升到 3.6。离实时还有距离，但已经能用了。

成本收益算了下，开发两个月，代码 4800 行，包括多种模式组合、前向反向、测试。性能提升 2 倍，光流服务吞吐量提升 50%。Grid Sample 在图像配准、视频稳定、风格迁移都能用，复用价值高。

后续优化还想试试，融合 Grid Sample 和后面的卷积，warping 完直接卷积。还想研究 3D Grid Sample，体数据的采样，医学影像用得多。这些列在计划里，有空再搞。

文档整理了完整的开发笔记，坐标归一化的公式、不同模式的实现、梯度推导都详细记录了。18 种模式组合的测试结果也列了表格。踩过的坑写成了 FAQ，align_corners、padding_mode、边界情况这些细节。代码注释很详细，关键函数都解释了数学原理。
